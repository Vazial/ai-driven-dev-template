# ADR-0001: 会議室予約フロントエンドの設計パックとしてシンプルCRUDパックを選定する

## 文脈

meta/architecture-selection.md の複雑度評価チェックリストに沿って、architectが会議室予約システムの
フロントエンドの特性を評価した。対象は既に承認済み・実装済みの会議室予約バックエンド
（projects/reservation-system、垂直スライス4本 RSV-C/K/A/R が全段緑・マージ済み）に対する利用者向け
画面であり、業務ルール（重複予約禁止・時間帯の妥当性・営業時間・定員・キャンセル期限等）はすべて
バックエンド側のドメインモデルパック（projects/reservation-system/adr/0001）に既に凝集され、契約
（projects/reservation-system/contracts/reservation-api.yaml）として確定・承認済みである。

| 評価軸 | 評価 |
|---|---|
| 不変条件の量 | ほぼ無い。業務ルールの判定はすべてバックエンドAPIが行い、結果（成功/拒否理由コード）を返すだけ。フロントエンドが自前で守る不変条件はない |
| 状態遷移の複雑さ | 低い。画面が持つ状態は「未入力→送信中→成功/失敗」程度の表示状態にとどまる。予約自体の状態遷移（作成・キャンセル等）はバックエンドが保持し、フロントエンドは複製しない |
| ルールの変更頻度 | バックエンド契約（reservation-api.yaml）は4スライス分の改訂を経て安定運用中。画面の見せ方は変わりうるが、それは業務ルールの変更ではない |
| CRUD比率 | 高い。既存4エンドポイント（予約作成・キャンセル・空き状況確認・予約ルール確認）に対する薄いフォーム/一覧/詳細表示が中心 |
| 連携中心か計算中心か | 連携中心。独自の業務計算はほぼ持たず、既存APIへの入出力の橋渡しが主体 |
| データ特性 | 単一利用者の対話的操作。バッチ・ストリーム処理はない |

## 決定

**シンプルCRUDパック**を、フロントエンド向けに翻訳して採用する。

- 層は圧縮する: 画面コンポーネント → （契約から生成したAPIクライアント）という薄い構成とし、独自の
  ドメイン層・重量級の状態管理フレームワークは置かない（architecture-selection.md 4節「Transaction
  Script、薄いサービス層、生成系ツール活用」のフロントエンド版）
- 生成系ツールの活用を必須とする: reservation-api.yaml（バックエンド契約原本）からの型・クライアント
  自動生成でL3（境界の整合）を担保する。API仕様は複製しない（SSOTはreservation-systemが持つ）
- 受け入れテスト（L4）は「主要フローに限定」する（verification.md L4詳細）。バックエンドが既に検証済み
  の業務ルールの正しさ（時間帯計算のロジック等）をフロントエンドのE2Eで再検証しない。フロントエンドの
  受け入れシナリオは「画面がAPIの成功/空/拒否のそれぞれの応答を、利用者に正しく伝えるか」を対象とする
- 具体的な言語・フレームワーク・ディレクトリ構成は、本ADR承認後に別ADR（スタック選定）およびdesign.md
  で確定する

## 検討した代替案

- 案A: フロント主体パック / 不採用の理由: architecture-selection.md 4節の定義は「ロジックの大半がUIに
  あるツール・可視化」向け。本件は業務ロジックの大半が既にバックエンドのドメインモデルパックに存在し、
  フロントエンドはその薄い窓口にすぎないため、名称の直感に反して不適合と判断した。今後、画面側に独自の
  複雑な状態管理やクライアント側ロジック（例: オフライン編集、複数会議室の横断的な可視化）が必要になれば、
  その時点でパックの乗り換えを検討する
- 案B: 軽量ドメインモデルパック / 不採用の理由: フロントエンドが自前で守る不変条件が実質的にない（すべて
  バックエンドが判定済み）ため、値オブジェクト・集約に相当する構造を設けるコストに見合わない
- 案C: バックエンドと同じドメインモデルパック / 不採用の理由: 過剰設計。業務ルールの二重実装（バックエンド
  とフロントエンドで同じ判定ロジックを持つ）はドリフトのリスクを生み、SSOT（P-03）を損なう

## 帰結

- 良い影響: 契約（reservation-api.yaml）への忠実な薄いバインディングに集中でき、業務ルールの二重実装を
  避けられる。バックエンド側でルールが変わっても、応答の形が変わらない限りフロントエンドは無修正で追従できる
- トレードオフ: 画面側の入力検証は「利用者体験のための先読みチェック」にとどまり、最終的な正しさの判定は
  常にAPI応答に委ねる設計になる（画面単独では完結しない即時フィードバックが持てない場面がある）。将来、
  画面側に独自の複雑なロジックが必要になったら、パックの再選定が要る
- 波及する作業: 実装スタックの確定（別ADR）、ディレクトリ構成規約の確定（別ADR）、design.md/ARCHITECTURE.md
  の新規作成（いずれもADR承認後にarchitectが着手）
