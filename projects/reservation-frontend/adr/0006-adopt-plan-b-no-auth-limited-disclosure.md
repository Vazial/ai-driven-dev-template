# ADR-0006: 認証方針として「案B（無認証・情報を絞る）」を当面採用する。案C（軽量認証）は将来オプションとして残す

> **承認者向けサマリ**: 会議室予約フロントエンドは、当面「認証を導入せず、代わりに画面が見せる情報を
> 絞る」方針（案B）を採る。予約者名は画面に表示しない、自分の予約一覧は端末（ブラウザ）内だけで管理し
> サーバの一覧APIは持たない、という2点が具体的な中身。この決定により、バックエンド契約（`reservation-
> system/contracts/reservation-api.yaml`）の変更は不要になり、既存の関連ADR（`reservation-system/
> adr/0003`・`0005`・`0006`）はいずれも無変更のまま維持される。将来、予約者名の表示や端末をまたいだ
> 自分の予約の閲覧が必要になった場合は、軽量認証を導入する案C（本ADRでは採らない）を新しい決定として
> 検討する。

## 文脈

architectが`design/reconciliation/booking-design-reconciliation.md`で行った、外部AI設計成果物
`src/design-preview/BookingDesign.tsx`と契約の突き合わせにおいて、**最大の分岐**として次を指摘していた
（項目15・16）:

- 現行のバックエンド契約は`reserverId`を無認証・自由入力の自己申告として扱う設計になっている
  （`reservation-system/adr/0003`「予約者を社員に限定せず一般化する」。この決定自体は資格・認証の
  ルールを持たないことを明示している）
- BookingDesign.tsxは、この無認証の前提の上に「予約者名（`reserverName`）をタイムラインに表示する」
  「`reserverId`の一致で自分の予約一覧を絞り込む」という機能を乗せている
- 認証を導入しない限り、`reserverId`を自由に書き換えられる入力欄（設計のヘッダー部）を使って、他人の
  `reserverId`を入力するだけで他人の予約一覧を閲覧できる、なりすまし・覗き見のリスクが生じる
- この分岐の結論次第で、新規API3件（`GET /reservations?date=`・`GET /reservations?reserverId=`）の
  採否、`reserverName`フィールドの契約化、そして`reservation-system/adr/0006`（空き枠のみを返す、
  占有情報は返さない、という既に人間裁定済みの決定）を再検討するかどうかが変わる、と整理されていた

人間はこの分岐に対して、**案B（無認証を維持しつつ、情報公開範囲を絞る）を当面採用し、案C（軽量認証を
導入する）は将来検討として明示的に残す**、という決定を下した。

## 決定

**認証方針として案Bを当面採用する。** 具体的には次の4点:

1. **予約者名を画面に表示しない**。タイムラインの予約バーは「空き」「予約済み（不可）」という状態
   表示にとどめ、誰の予約かは示さない
2. **「自分の予約」は端末ローカル（`localStorage`等のクライアント内ストレージ）で管理する**。サーバ
   に「予約者ごとの一覧を返すAPI」は持たせない
3. **占有情報（誰が・いつ押さえているか）を返す新規API、および`reservation-system/adr/0006`
   （空き枠のみを返す設計）の再検討は行わない**。タイムラインの「空き/不可」の状態は、既存の
   `GET /rooms/{roomId}/availability`が返す`availableSlots`（空いている時間帯）から**空き以外＝不可**
   として導出する。個々の予約の境界・予約者情報は扱わない（`availableSlots`がRSV-A-03により隣接する
   複数予約を1つの「空きなし」区間として融合してしまう制約とも、この設計は正面から衝突しない——
   融合されても「不可」という状態自体は変わらないため）
4. **`reserverName`（表示用の氏名相当フィールド）は`reservation-api.yaml`に追加しない**

**案Cの位置づけ（将来オプションとして明示的に残す）**: 将来、軽量認証（例: `reserverId`に対する資格
確認、セッション・トークンの導入等）を採用する場合、次が可能になり、かつ次の追加作業が必要になる。

- 可能になること: 予約者名（または表示用のニックネーム等）をタイムラインに表示できる。端末をまたいで
  自分の予約を一覧できる（サーバ側の一覧APIが正当化される）
- 必要になる追加作業: 認証・資格確認の基盤導入、`reserverId`の資格検証ロジック（バックエンド）、
  `POST /reservations`・`POST /reservations/{id}/cancel`への認証情報の付与方法の設計、新規API
  （`GET /reservations?date=`・`GET /reservations?reserverId=`）の契約化。これらはいずれも新しい
  スライスの契約とADRとして扱う（`reservation-system/adr/0003`が既に「将来『誰が予約できるか』の
  ルールを導入する場合は新しいスライスの契約とADRで扱う」と述べている通り）

## 検討した代替案

- 案A: 無認証のまま情報も絞らない（BookingDesign.tsxの設計をそのまま採用し、予約者名表示・
  `reserverId`ベースの閲覧を維持する） / 不採用の理由: なりすまし・覗き見のリスクが残ったままになる
  （reconciliation項目15・16が指摘した問題そのもの）
- 案C: 軽量認証を今回のスライスで導入する / **不採用（今回は。将来検討として残す）**: 認証基盤の追加は
  `reservation-frontend/adr/0001`（シンプルCRUDパック。「フロントエンドが自前で守る不変条件は実質的に
  無い」という評価軸に基づく選定）が想定するスコープを超える重い決定であり、バックエンド契約側にも
  資格検証ロジックの追加を要求する。当面は情報を絞ることでリスクを回避し、認証が必要になった時点で
  改めて評価する方が、現時点の投資対効果に見合う
- **案B（採用）**: 無認証を維持しつつ、個人を特定できる情報（予約者名）の露出と、他人が閲覧できる
  情報（サーバ側の予約者別一覧）を絞る。契約変更を最小化しつつ、プライバシーリスクを回避できる

## 帰結

- **バックエンド契約（`reservation-system/contracts/reservation-api.yaml`）への変更は発生しない**。
  `reserverName`フィールドの追加、`GET /reservations?date=`・`GET /reservations?reserverId=`の新設は
  いずれも不要になった
- **`reservation-system`側の既存ADRはいずれも無変更・維持される**: `adr/0003`（予約者の一般化・
  無認証の前提）、`adr/0005`（キャンセルは本人のみ・`reserverId`一致判定）、`adr/0006`（空き枠のみを
  返す設計）。本ADRはこれらを覆さない。**本ADRは`reservation-frontend`スコープの決定であり、
  `reservation-system`側のADRを編集・superseded化しない**（P-06）
- `src/design-preview/BookingDesign.tsx`に対しては、骨格（主要なUIブロックの構成）を保ったままの設計
  調整が発生する。具体的な調整項目は`design/reconciliation/booking-design-reconciliation.md`
  「9. 案Bが要求する設計調整（骨格内）」に列挙した（本ADRでは実装しない。次の洗練作業の対象）
- **本決定と独立に残る未決事項**: `GET /rooms`（会議室一覧、認証方針とは無関係に必要性がある論点）の
  採否、`PATCH /reservations/{id}`（時間変更）の機能自体の要否。いずれも本ADRでは扱わない
  （reconciliationの残未決として引き続き人間判断待ち）
- 良い影響: 契約変更なしで、なりすまし・覗き見リスクを回避できる。ADR-0001が想定する「フロントエンドは
  薄いバインディング」というスコープを維持できる
- トレードオフ: 「誰が押さえているか」が分からないため、同僚同士での調整（口頭確認等）に頼る場面が
  残る。自分の予約が端末ローカル管理のため、別の端末・ブラウザからは見えない（案Cへの移行までの間の
  既知の制約として受け入れる）
