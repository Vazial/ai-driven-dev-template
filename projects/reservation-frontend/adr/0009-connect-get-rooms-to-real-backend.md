# ADR-0009: `GET /rooms`(RSV-L)を初の実バックエンド接続とする方針を定める

> **承認者向けサマリ**: フロントは今まで一度も実APIを叩いていない（全て`src/api/`のモック）。今回、
> 最小スライスとして`GET /rooms`（RSV-L、バック実装済み・main）**1本だけ**を実接続する
> （`meta/adr/0023`が定めるクロスプロジェクトの2つ目の交点＝E2E結合の初適用）。方針は次の5点。
> **(1)** モックを既定・恒常の構成として残し、実APIは環境変数で明示的に有効化する切替式にする。
> **(2)** 接続経路はVite dev serverのproxyとし、**バックエンド（CORS等）は変更しない**——越境
> （`meta/adr/0023`のauthorizeゲート）は今回発生させない。**(3)** E2E（Playwright、4件）は当面
> モック構成のまま据え置き、CIにPostgreSQL/Springを足さない。実接続はCIの外、orchestratorによる
> 一回限りの走破（`meta/adr/0024`）で確認する。**(4)** ネットワーク層の失敗（未起動・接続不可）は
> `ApiResult<T>`のHTTP拒否レスポンス（`ProblemResponse`）とは別物として扱い、契約型を拡張しない。
> **(5)** 走破の成功基準は「実DBに投入した会議室データが画面に表示される」こと。実装詳細（環境変数名・
> proxy設定・エラー表示文言）はdeveloperに委ねる。
> **(6)** 決定3・5は無期限の先送りではない——**(a)実API接続を既定にする時／(b)2本目のAPIを実接続
> する時**に結合の回帰ゲートを設計する（人間の承認条件として追加）。形のドリフトはyaml（SSoT）を
> 介して両側が別々に機械ゲートされているため推移的に保証済みであり、走破でしか確認できないのは
> 配線のみ、という前提が(a)(b)で崩れるため。

## 文脈

人間の決定（前提、再導出しない）: 「フロントとバックの初の連動をやる。うまくいくかデータを取りたい」。
最小スライスとして`GET /rooms`1本だけを実接続する。他API（availability・reservations・cancel・
rules）は今回接続しない。

現状（orchestrator調査済み）: フロントは`fetch`/`VITE_`環境変数/baseURLの類を一度も持たない。
`src/api/rooms.ts`の`listRooms(): Promise<RoomSummary[]>`は既に、内部でモックの
`RoomListResponse`（`{rooms:[...]}`）を組み立て`.rooms`を剥離するアダプタ構造になっている
（公開シグネチャを変えず内部だけ差し替えられる）。型は`reservation-api.yaml`（SSoT）から生成済み
（ADR-0008）。バックは`GET /rooms`実装済み・L0–L4緑・main（ポート8080既定、Spring Boot、
PostgreSQL必須、CORS設定なし、`server.servlet.context-path`なし=`/rooms`直下）。`vite.config.ts`に
proxy設定はない。PlaywrightのE2E（`e2e/helpers.ts`の`injectReservation`）は、Vite dev serverが
ソースをそのままESモジュール配信する性質を使い、ブラウザ内モックモジュールへ直接予約を注入する
方式であり、実APIへの切替とは原理的に両立しない構造になっている。

## 決定

以下5点は本ADRの新規論点であり、architectが論点整理・推奨を行った上で人間承認を求める。

### 1. モックと実APIの共存方式: 既定モック・切替は環境変数

**推奨: 全面切替ではなく、環境変数による切替式。既定値は「未設定＝モック」とする。**

- モックは今後も**恒常の構成**として残す。Vitest（42件、DB不要・高速）・通常の`npm run dev`・CIは
  今まで通りモックのみで完結させる。理由: 実APIを既定にすると、フロント単体の開発・CIが常時
  PostgreSQL＋Spring起動を要求するようになり、今回接続するのが1本のAPIに過ぎないこととコストが
  釣り合わない
- `src/api/rooms.ts`の`listRooms()`は、公開シグネチャ`Promise<RoomSummary[]>`を変えないまま、
  内部で「環境変数が実APIを指す設定を持つ場合は実fetch、そうでなければ既存のモック組み立て」を
  分岐するアダプタに拡張する（既にモックとの分離ができているため、この分岐の追加コストは小さい）。
  変数名・分岐実装の具体形はdeveloperに委ねる
- モックの位置づけ: 「実APIが無い間の代用品」ではなく、**単体テスト・通常開発の既定手段として今後も
  併存し続けるもの**。実API接続はオプトインの検証手段という非対称な関係にする

### 2. 接続経路: Vite dev server proxy。バックエンド（CORS）は変更しない

**推奨: `vite.config.ts`の`server.proxy`で`/rooms`を`http://localhost:8080`へプロキシし、
ブラウザからは同一オリジンに見せる。バックエンドへのCORS設定追加は行わない。**

- 理由: proxy方式はフロント側の変更のみで完結し、バックエンドを一切触らずに済む。バックエンドを
  変更する選択肢（CORS設定の追加）は`meta/adr/0023`が定める越境（人間のauthorizeを経てarchitectが
  直接起草してよい）に該当する重い経路であり、フロント側だけで達成できる手段がある以上、今回は
  越境を発生させない方が筋が良い
- 本番構成（将来）は、実際のデプロイ形態（同一オリジンでのリバースプロキシ、別ドメイン+CORS等）に
  依存し、今回のスライスでは決めない（P-02、過剰な先回りをしない）。1点だけ明記: proxy方式は開発時
  専用の仕組みであり、本番の疎通方式を先取りするものではない

### 3. E2E(L4)への影響: 当面モック構成のまま据え置く。CIは変えない

**推奨: Playwright(4件)・`playwright.config.ts`は今回変更しない。E2Eは実装後もモックのroomsを
使い続ける構成のままとし、rooms実API・reservations系モックという混在は今回作らない。**

- 理由: `injectReservation`（RFE-B-03の二重予約シナリオが依存）はブラウザ内モックモジュールへの
  直接注入に依存しており、実バックエンドに置き換えると同じ手段で二重予約状態を安定再現できなくなる。
  この依存を崩さずに済ませるには、E2Eの対象を丸ごとモック構成に留めるのが最も単純
- CIにPostgreSQL＋Spring起動を足すことは、今回のスコープ外と判断する。理由は2つ: (a)今回接続する
  のは`GET /rooms`1本のみであり、E2E全体の実バックエンド化はスコープ超過（P-02）、(b)RFE-B-03の
  再現手段が実API環境で未確立のまま導入すると、既存4件の安定性を壊すリスクが実利益を上回る
- 実接続の確認は自動テストではなく、下記5節の走破で行う

### 4. 失敗時の扱い: ネットワーク層の失敗は`ApiResult<T>`を拡張しない

**推奨: `ApiResult<T>`（`{ok:false, error:ProblemResponse}`）はHTTPの拒否レスポンス（サーバが
応答した契約形状のエラー）専用のまま維持する。ネットワーク層の失敗（未起動・接続不可・タイムアウト）
はこれとは別物として扱い、契約型を拡張しない。**

- 実装方針: 実API版`listRooms()`の内部で、`fetch`自体が失敗する（例外）場合はそのまま呼び出し元に
  伝播させ（reject）、画面側で最小限の汎用失敗表示（例:「読み込みに失敗しました」）を出す。
  `ProblemResponse`の型（契約が定義する構造化エラー）に無理に押し込めない
- 理由: `ProblemResponse`はバックエンドが実際に返す契約形状であり、バックが応答すらできない状態
  （ネットワーク不通）をこの型で表現しようとすると、契約に存在しない意味をAPI型に持ち込むことになる。
  P-05（摩擦が発生してから足す）にも照らし、今回は最小限の分離のみ決め、詳細表示文言・リトライ等の
  設計はdeveloperに委ねる

### 5. 検証方法: 「うまくいった」と何をもって言えるか

**推奨: 実DBに投入した会議室データが、実際に画面の会議室一覧として表示されることを、orchestrator
が両方起動して確認する一回限りの走破（`meta/adr/0024`の走破に相当）とする。新規の自動テストは
作らない。**

- 具体的な確認手順の骨子: (a) reservation-systemをPostgreSQL込みで起動しRSV-L相当のデータを
  投入（モックの固定値`MOCK_ROOMS`とは異なる名称にしておくと、モック経由でないことが目視で判別
  できる）、(b) reservation-frontendを実API接続モードで起動、(c) ブラウザで会議室一覧画面を開き、
  投入したデータが表示されることを目視確認する
- 走破の実施主体・最終判断は`meta/adr/0024`の既定通り: 実施はorchestrator（ブラウザ操作ツールを
  持つ）、最終判断は人間
- 成功した事実はactiveContext.mdに記録する。CIのジョブとして組み込む・恒常化することは今回は
  行わない（P-05、必要になれば別途検討）

### 6. 本方針が不足になる条件（先送りの期限を明示する）

決定3・5（E2Eはモック据え置き・走破のみで自動テストを新設しない）は**無期限の先送りではない**。
次のいずれかに至った時点で、結合の回帰ゲートを設計する:

- **(a) 実API接続を既定にする時**（環境変数によるopt-inをやめ、アプリが実バックエンド前提で動く時）
- **(b) 2本目のAPIを実接続する時**（`GET /rooms`以外が実APIに乗る時）

**なぜこの2条件か**: 現時点で形（レスポンス構造）のドリフトは、両側を同時に起動しなくても既に
機械的に検出される——バックはL4で`OpenApiInteractionValidator`がyaml原本に対して応答を照合し
（`RoomListDsl`）、フロントは型をyamlから生成しているため使い方がズレれば`npm run build`が落ちる
（ADR-0008）。すなわち**yaml（SSoT）を介して両側が別々に機械ゲートされており、形の互換性は推移的に
保証されている**。走破でしか確認できないのは配線（proxy設定・URLパス・CORS・fetch実装・環境変数名）
であり、それは実API経路が**opt-in＝まだ誰の既定経路でもない**うちは、壊れても影響が有効化した本人に
限られ即座に気づける。この前提が崩れるのが上記(a)(b)である。

**走破の実測結果（2026-07-28、orchestrator実施）**: 決定5の走破を実施し、**成功基準を満たした**——
実DBに投入した会議室（`実DB会議室オリオン`・`実DB会議室ペガサス`、モックの`MOCK_ROOMS`とは別名）が
実際に画面へ表示され、モック由来の名前（`会議室A`/`会議室B`）は画面に一切現れなかった。proxy・
生成型・name昇順・fetch配線がいずれも実地で機能することを確認した。走破時に判明した実務的な事項も
記録する: (1) `TestSupportController`は`@Profile("acceptance")`のため、走破用のデータ投入には
バックエンドをacceptanceプロファイルで起動する必要がある、(2) 本環境ではPodmanのポート転送がIPv6
側に出るため、JDBC URLを`jdbc:postgresql://[::1]:5432/...`にする必要があった（環境固有）。

**走破で判明した想定外の帰結（重要）**: `GET /rooms`だけを実APIにすると、**画面は機能しない状態に
なる**。実DBのroomIdはサーバ採番のUUID（例`660a5b6d-…`）である一方、`GET /rooms/{roomId}/availability`
はモックのままで`MOCK_ROOMS`（`room-a`/`room-b`）を探すため、実DBのUUIDでは必ず`ROOM_NOT_FOUND`に
なり、各会議室に「会議室が存在しません」と表示されタイムラインが空になる。これはバグではなく、
**roomIdの名前空間が実DB側へ移ったことによる必然**である。すなわち`GET /rooms`単独の実接続は
「配線の検証」としては成立するが「画面として使える構成」ではない。したがって決定6の条件(b)
（2本目のAPIを実接続する時）は、当初の想定より早く——**実APIを実用的に使うなら
`GET /rooms/{roomId}/availability`と同時に接続する必要がある**——到来することが実測で判明した。
次スライスの候補として記録する（本ADRではその設計まで行わない。P-02）。

**その時に設計すべきもの**: 結合の回帰ゲートは、`meta/adr/0026`が定めたCI分割
（`govlint.yml`＝共有／`ci-<project>.yml`＝自プロジェクト配下のみ）の**どちらにも属さない**。
両プロジェクトのpathsで起動する第3のワークフロー（例: `ci-integration.yml`）が要る。すなわち
`meta/adr/0026`は結合テストの置き場を定義していないという穴があり、(a)(b)に至った時点でその
穴を埋める設計（meta層の追補）も同時に必要になる。本ADRはこの宿題の存在を記録するに留める。

## 検討した代替案

- 案A（1節）: 全面切替（モックを廃止し常に実API必須にする）/ 不採用: Vitest・通常開発・CIが
  常時PostgreSQL＋Spring起動を要求するようになり、今回接続する1本のAPIに見合わないコスト増になる
- 案B（2節）: バックエンドにCORS設定を追加し、ブラウザから直接叩く / 不採用: フロント側だけで
  達成できる手段（proxy）がある以上、バックエンドを変更し越境（`meta/adr/0023`のauthorizeゲート）
  を発生させる理由がない。将来、本番構成上proxyが使えない事情が判明すれば再検討の余地は残す
- 案C（3節）: E2Eも実バックエンドに切り替え、`injectReservation`を別手段（例: 実APIへの直接POST）
  に置き換える / 不採用（今回）: 今回のスコープは`GET /rooms`1本であり、二重予約シナリオの再現
  手段を作り直すのはスコープ超過。CIにPostgreSQL＋Springを足すコストも見合わない
- 案D（4節）: `ApiResult<T>`にネットワーク層の失敗を表す第3の状態を追加する（例:
  `{ok:false, kind:"network"}`） / 不採用（今回）: 契約型（`ProblemResponse`）にバックエンドが
  実際に定義していない意味を持ち込むことになり、SSoT一元化（`meta/adr/0025`）の精神に反する。
  UI層の一時的な例外処理で足りる範囲であり、契約を膨らませてまで解く必要がない
- 案E（5節）: 自動化されたスモークテスト（実バックエンド込みのCI専用ジョブ）を新設する /
  不採用（今回）: `meta/adr/0024`のコスト方針（ツールは作らない、規約と手順の追加に留める）と
  同じ理由で、今回は一回限りの走破で足りると判断する。必要性が繰り返し実証されれば再検討する

## 帰結

- developer宿題: `src/api/rooms.ts`の実API分岐実装、`vite.config.ts`へのproxy追加、環境変数名の
  確定、画面側の汎用失敗表示の実装。いずれも本ADR承認後の実装スライスで着手する
- `reservation-system`側の変更は発生しない（越境なし）。既存ADR（`reservation-system/adr/0003`・
  `0005`・`0006`・RSV-L関連ADR）はいずれも無変更のまま維持される
- Playwright(4件)・`playwright.config.ts`・E2Eの構成は本ADRでは変更しない
- 人間承認事項: 上記5方針そのもの（1: 環境変数切替式／2: proxy採用・CORS変更なし／3: E2E据え置き・
  CI不変／4: ネットワーク失敗を契約型に含めない／5: 走破による検証・自動テスト新設なし）
- 矛盾チェック: `adr/0003`（L3構想）・`adr/0006`（案B・無認証）・`adr/0008`（生成方式）・
  `meta/adr/0022`（2断面）・`meta/adr/0023`（consumer-driven・縦順序・越境の実行主体）・
  `meta/adr/0025`（SSoT一元化）のいずれとも矛盾しない。本ADRは`meta/adr/0023`が図示した「2つ目の
  交点＝最後のE2E結合」の初適用にあたる
