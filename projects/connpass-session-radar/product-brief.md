# Product Brief — 毎朝、条件に合うconnpassイベントを配るレーダー

> **承認者向けサマリ**: connpassを見に行かなくて済むようにするためのプロダクトである。リポジトリ内の
> YAMLに書いた興味の条件（キーワード・地域・オンライン可否・グループ）に合うイベントを、毎朝1回、
> 通知先へ一覧で届ける。申し込みはconnpassの当該ページで利用者自身が行う。画面は持たない。
> **通知済みイベントを記録せず、毎朝その日の条件で出し直す**。

> **状態**: **未承認のドラフト**。2026-08-16に人間とのユースケース整理で確定した内容を書き起こした
> ものであり、まだ承認されていない。このブリーフの承認は、後続の契約・ADR・実装の承認を意味しない。

> **前身との関係**: `meta/scenario-id-prefixes.md` のCSR行（2026-08-15、PR #100）は本プロジェクトを
> 「Connpassの興味深いセッションを見つける**画面**。`CSR-B`(セッション閲覧)」と記録している。
> 2026-08-16に人間が画面を持たない方針へ改めたため、**その備考は本ブリーフと食い違っている**。
> 台帳の訂正は `meta/**` の直列化対象として別PRで行う（meta/adr/0026 決定4）。

## 1. 目的と利用者

**解く問題は「探す手間」である。** connpassを開いて検索し、絞り込み、見比べるという行為そのものを
なくす。利用者は自分のために使う一人であり、他人へ配信する運用は初期スコープに含めない。

**新着の速報性は主目的ではない。** 「気づいたら満席だった」を防ぐことより、「そもそも見に行かなくて
よい」ことを取る。したがって品質軸は**絞り込みの精度と、届いた一覧の読みやすさ**であって、検知の
速さではない。この選択は、通知済みイベントを記録しないという設計判断（§2）と対になっている。

## 2. 中心となる体験

1. 利用者は興味の条件をリポジトリ内のYAMLに書き、commitする。
2. 毎朝1回、アプリが条件に合うイベントをconnpass APIから取得する。
3. 条件に合うイベントの一覧が、通知先へ1通で届く。
4. 気になるイベントがあれば、利用者は一覧中のリンクからconnpassのページを開き、**自分で申し込む**。

**状態を持たない。** 通知済みイベントのIDを永続化せず、毎朝その日の条件で改めて出し直す。同じ
イベントが複数日にわたって載ることを許容する代わりに、永続ストアと「既読」の概念が丸ごと不要に
なる。これは「今日の一覧」型であって、新着差分の速報ではない。§1で速報性を主目的から外したのは
この判断と対になっている。

**条件の変更手段はYAMLのcommitである。** 画面も設定コマンドも持たない。変更の履歴がgitに残ることを
利点として取り、その代わり「出先で条件を変える」ことはできない。

## 3. 届ける情報

一覧の各イベントには、**開くかどうかを判断するために必要な情報だけ**を載せる。connpass APIから
取得できる事実に限り、推測・断定はしない。

- イベント名（`title`）
- 開催日時（`started_at`。ISO-8601。取得できない場合がある）
- 開催場所（`place` / `address`）、またはオンラインであること
- 主催グループ名（`group.title`。グループに属さないイベントもある）
- 定員と参加者数から算出した残席の目安（`limit - accepted`）。**`limit` が null のとき＝定員なし**は
  その旨を示し、数値を作らない。補欠者数（`waiting`）があれば満席の判断に使う
- connpassのイベントページへのリンク（`url`）——申し込みと詳細確認の導線

**中止されたイベント（`open_status = cancelled`）は載せない。** 中止済みが一覧に混ざると、一覧を
信頼して読めなくなるためである。

**connpass外で申し込むイベント（`event_type = advertisement`）も、同列に並べる**（2026-08-16、
人間の判断）。これは「どこにも申し込めない」イベントではなく、connpassに参加ボタンが無く主催者の
別サイトで受け付けているものであり、**リンクをたどれば申し込める以上、区別する理由がない**という
判断による。したがって節や印で分けない。

ただし帰結が1つある——**connpass側に参加受付が無い以上、参加者数・定員が意味を持たない**。この種の
イベントでは**残席の行を出さない**（0席や「残り0」と書かない。取得できない事実を数値にしない）。

## 4. 外部データと公開リポジトリの境界

イベント情報源は **connpass API v2 のみ**とする。一次情報は `connpass-api-v2-facts.md`。

- **APIキーはリポジトリに置かない。** `X-API-Key` ヘッダはサーバー／実行環境からconnpassへだけ送り、
  キー入りのURL・ログ・エラー・トレースをGitに出さない（meta/adr/0040）
- **スクレイピングを行わない。** API以外の手段によるクローリング・スクレイピングは、自動化の有無に
  かかわらずconnpassの利用規約で禁止されている。**APIで取れないものはHTMLから取らない**
- **APIキーは個人・コミュニティ申請では1本のみ**で追加できず、**1秒1リクエスト**の制限がかかる。
  並列化で回避できないため、この制限は取得戦略そのものを縛る（§7-3）
- イベント本文・画像の複製と再配布は行わない。一覧はconnpassのページへ送る導線であり、
  connpassの内容を代替するものではない
- 通知先のトークン・Webhook URLも同様に秘密として扱い、Gitに置かない

## 5. 画面を持たないこと

このプロダクトは画面を持たない。したがって標準フロー（meta/agents.md §4）に designer は登場せず、
断面①（骨格合意）は API形状＋ADR のみで完結する（meta/adr/0022）。

「一覧を見返したい」という要求は、通知先（LINEまたはSlack）の履歴が担う。アプリ側に閲覧画面を
持たせない判断であり、再検討には新たな人の意思決定とADRを必要とする。

## 6. 通知の頻度と沈黙の意味（2026-08-16、人間の判断）

**毎朝、必ず1通届く。** 条件に合うイベントが0件の朝も「今日は0件」と送る。取得や通知に失敗した朝も
「失敗した」と送る。

この2つを合わせると、**「通知が来ない朝」に意味が固定される**——0件でも失敗でもなく、**仕組み自体が
動いていない**という合図になる。沈黙が3つの意味（0件・失敗・停止）を持たないようにするための判断で
あり、静けさより判別可能性を取っている。

**原理的な限界を明示する**: 通知の送信経路そのものが壊れている場合、失敗通知も届かない。この場合の
検知は「毎朝来るはずのものが来ない」という利用者の気づきに委ねる。実行基盤側の失敗検知を併用するか
どうかは、定期実行のトリガ選定（§7-2）と一体で判断する。

## 7. 未決事項

1. **通知先**。普段使いはLINEだが、LINE Messaging API（LINE Notifyは2025年に終了済み）とSlack
   Incoming Webhookの**実装難度・必要な秘密・整形能力**を比較したうえで人間が決める。どちらに
   決まっても差し替えられる境界を設計に持たせる。アーキテクチャ選定ADRの決定事項とする
2. **定期実行のトリガ**（cron／GitHub Actions／常駐）と、無料枠で成立するか。§6の「送信経路ごと
   壊れた場合」の検知をここで補えるかも併せて見る
3. **何日先までを配るか**。connpass APIには**開催日の範囲指定が無く**、`ymd`（年月日）か `ym`（年月）の
   ピンポイント指定しかない。ただし `ymd` は配列パラメータであり、**1リクエストに複数日を渡せる**
   （`ymd=v1,v2` の記法が明記されている）。したがってリクエスト回数を決めるのは日数ではなく、
   **1回100件という上限に対する該当件数**である。取得戦略と一体で決める。
   **訂正（2026-08-16）**: 本項は当初「Nがそのままリクエスト回数＝所要時間に跳ね返る」と記していたが、
   これは誤りだった。`ymd` の複数値が1リクエストに収まる点を見落としていた。ADR-0001の起草中に
   architectが一次情報との矛盾として指摘した

## 8. 初期スコープから除外するもの

- **申し込み・キャンセルの自動化**。connpass APIは読み取り専用であり、申込・キャンセルのエンドポイント
  が存在しない。利用者がconnpassのページで行う
- **参加者一覧の表示**。取得するAPIが無い
- **画面**（§5）
- **既読・通知済みの管理**（§2）。状態を持たない設計を選んだ結果として除外される
- **除外語（「この言葉が入っていたら要らない」）の仕組み**（2026-08-16、人間の判断）。connpass APIに
  NOT条件が無いため自前フィルタになるが、まずは探す言葉と場所だけで運用し、**実際に邪魔だと分かって
  から足す**。設定に書く項目を増やさないことを優先した判断であり、除外が必要になった時点で
  新たな意思決定として追加できる
- **生成AIによるイベントの選定・要約**。絞り込みはYAMLに書いた条件による説明可能なルールだけで行う
- **複数人への配信・購読管理**
- **connpass以外のイベントソース**

## 9. 受け入れの目安

- 毎朝、YAMLに書いた条件に合うイベントの一覧が通知先に1通届く
- 一覧の各イベントについて、開催日時・場所（またはオンライン）・主催グループ・残席の目安・
  connpassへのリンクが分かる
- **条件に合うイベントが0件の朝も、「0件」と分かる通知が1通届く**
- **取得や通知に失敗した朝も、「失敗した」と分かる通知が1通届く**（送信経路ごと壊れた場合を除く。§6）
- connpassで申し込めるイベントと、外部サイトで申し込むイベントが同じ一覧に並ぶ。後者には残席の行が
  出ない
- 中止されたイベントが一覧に載らない
- 条件をYAMLで変えてcommitすると、翌朝の一覧に反映される
- APIキーと通知先の秘密がリポジトリに現れない
- connpassの1秒1リクエスト制限を超えない

## 10. このブリーフ承認後の順序

1. アーキテクチャ選定ADR（通知先の選定を含む。§7-1）を起こす。
2. 受け入れシナリオ（`CSR-*`）とAPI／入出力の契約を、このブリーフに沿って起こす。
3. 契約とADRの人間承認を経て、実装スライスへ進む。
