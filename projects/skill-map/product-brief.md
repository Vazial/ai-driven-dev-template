# Product Brief — 参加してきた勉強会から、自分の技術の地図を作る

> **承認者向けサマリ**: connpassの参加履歴・発表履歴から、**何をどれだけやってきたか**を1枚の地図に
> する。用途は3つある——**振り返る**（今年何をやったか）、**次を決める**（偏りを見て次に学ぶものを
> 選ぶ）、**見せる**（人に渡す名刺として使う）。3つ目を意識的に含めたことが、このプロダクトの
> 制約をほぼ決めている——**出力は人の目に触れる**ので、公開してよいのかという問いが最初に来る。
> 申し込み・キャンセルはしない。読み取りだけである。

> **状態**: **承認済み（2026-08-23）だが、着手できない。** 「何を作るか」は承認された。その直後に
> 規約を読んだところ、**本プロジェクトの用途は、いま持っているAPIキーが許された利用目的の範囲に
> 含まれない**ことが分かった（§4・§7-1）。**範囲が広がるまで実装に入らない。** ブリーフを残すのは、
> 次に同じ思いつきに至った人が調べ直さずに済むようにするためである。

## 1. 目的と利用者

**解く問題は「自分が何をやってきたか、自分でも把握できていない」こと。** connpassの参加履歴は
アカウントの中に時系列で積まれているが、**眺めても構造が見えない**。50件のイベント名の羅列から
「クラウドに偏っている」「今年はAIに寄った」「フロントエンドは3年触っていない」を読み取るのは、
人間がやるには向いていない作業である。

利用者は**本人**と、**本人が見せる相手**である。後者を初期スコープに入れたことが §4 の制約を生む。

### 3つの用途と、それぞれが要求するもの

| 用途 | 見たいもの | 効いてくる設計 |
|---|---|---|
| **振り返る** | 時系列。いつ何をやっていたか | 期間の区切り、密度の濃淡 |
| **次を決める** | 偏り。多い領域と、空白の領域 | 分類と集計。空白が見えること |
| **見せる（名刺）** | 一目で伝わる要約 | 見た目、公開できる形、載せてよい範囲 |

**3つは同じデータの別の切り口**であり、別々のプロダクトにはしない。ただし**「見せる」だけが外向き**
であり、他の2つには無い制約（§4）を持ち込む。

## 2. 中心となる体験

1. connpass APIから自分の参加履歴・発表履歴を取得する。
2. イベントを分類し、時系列と偏りが読める形に集計する。
3. 利用者はそれを見て、振り返り、次を決める。
4. 見せたい形が固まったら、**公開してよい範囲だけ**を人に見える場所へ置く。

**申し込み・キャンセルは行わない。** connpass APIは読み取り専用であり、そもそも手段が無い
（`projects/connpass-session-radar/connpass-api-v2-facts.md`）。

## 3. データ源

**connpass API v2 のみ**とする。一次情報は
`projects/connpass-session-radar/connpass-api-v2-facts.md`（同プロジェクトが取得・実測したもの。
本プロジェクトはそれを再定義せず参照する）。

- `GET /users/{nickname}/attended_events/` — 参加イベント
- `GET /users/{nickname}/presenter_events/` — 発表イベント

返るのはイベント検索と同じ完全なイベントオブジェクトで、`title` / `catch` / `description` /
`hash_tag` / `group`（id・title・url）/ `started_at` / `place` / `address` / `lat` / `lon` /
`accepted` がそろう。**分類の材料としては十分すぎる**。

**制約が2つある。** リクエストパラメータは `start` と `count` だけで**日付で絞れない**——期間を
限りたければ全件取ってから絞る。そして**1秒1リクエスト・1回100件**なので、履歴300件なら3リクエスト
＝3秒である。実用上の障害にはならない。

**未確認**: 「attended」が*参加登録した*を指すのか*受付された*を指すのかを定義した記述が無い。
キャンセルした申し込みの扱いも同様である。**この一点で地図の意味が変わる**ので、実装より先に実測する。

## 4. 公開の境界（このプロダクトで最も重い判断）

「見せる」を用途に含めた瞬間、**参加履歴が外に出る**。これは興味の条件を公開すること
（`projects/connpass-session-radar/adr/0004`）とは質が違う。

**興味は「何を知りたいか」だが、履歴は「実際に何をしたか」である。** 時系列に並ぶと、興味だけでは
出なかったものが読み取れる——空いている曜日と時間帯、物理的に足を運ぶ範囲、所属や職務の推測材料、
活動の濃淡から見える生活の変化。**消しにくさも違う**。興味条件は1回のcommitで消せるが、公開した
履歴は見た人の記憶に残る。

**自分だけの情報でもない。** 参加履歴は主催者名・グループ名・イベント名を伴う。リンクを張るだけなら
通常の引用の範囲だが、**集計して再掲するのは別の行為**である。

**規約を読んだ（2026-08-23）。結論は「公開の可否より手前で止まる」だった。**

読んだのは3本——サイトの利用規約、API利用規約、APIの案内ページ。**取得したデータの再配布・二次利用・
公開について、許す条文も禁じる条文も無い。** キャッシュ・保存についても、出典表記の義務についても
言及が無い。代わりに効く条文が2つあった。

- **サイト利用規約 第4条【権利の帰属】**——利用者がconnpassに記載した情報に発生する知的所有権は
  「すべて当社に帰属する」。**イベント名や概要はconnpassの著作物**という建て付けであり、リンクを
  張るのは通常の引用でも、まとめて再掲するのは別の行為になる
- **API利用規約 第9条【データの取扱い】第1項**——「利用者が同意した**利用目的以外の目的**で利用者情報を
  利用してはならず、第三者に譲渡、販売その他の行為を行わない」

**第9条が、公開の可否より手前でこのプロダクトを止める。** APIキーは申請のときに申告した利用目的の
範囲でしか使えず、**参加履歴の取得と分析はその範囲に含まれていない**。しかも**個人申請ではキーを
1本しか持てない**（追加不可）ため、用途ごとに申請し直して逃げることもできない。

したがって**現時点で本プロジェクトは着手できない**（§7-1）。公開の形をどうするかは、その先の問題で
ある——**キーの利用目的が広がって初めて、この節の判断が必要になる**。

参考までに、目的の問題が解けた場合の出口は次のとおり見立てている。第4条がある以上、**イベント名を
並べた地図を公開するのは灰色**であり、**自分の行動から導いた数字だけ**（「2026年: クラウド系12回・
AI系20回・フロントエンド0回」）なら第4条の射程から外れる。名刺としてはそれで足りる——「クラウドと
AIに寄っている」が伝わればよく、個々のイベント名は要らない。イベント名まで公開したいなら、規約に
明文が無い以上、推測で埋めずconnpassに直接聞く（P-08）。

**どの結論でも、振り返りと次を決めるという2つの用途は成立する。** 変わるのは出口だけである。

**秘密の扱い**は connpass-session-radar と同じ——APIキーをリポジトリに置かず、キー入りのURL・ログ・
エラーをGitに出さない（`meta/adr/0040`）。

## 5. connpass Session Radar との関係

**別プロジェクトである。** 同じAPIを使い同じ人が使うが、既存プロダクトの中心的な決定を3つとも
ひっくり返す。

| connpass Session Radar の決定 | 本プロジェクト |
|---|---|
| 画面を持たない | **見せるものを作る**＝何らかの表示を持つ |
| 状態を持たない（毎朝出し直す） | **履歴＝状態そのもの**を扱う |
| 解く問題は「探す手間」（これから行くもの） | 解く問題は「自分を知る」（もう行ったもの） |

**時間軸が逆である。** 一方は未来、もう一方は過去を見る。同じプロジェクトに入れると、承認済みの
中心的判断3つの再承認が同時に走る。

**共有するのは事実の文書だけ**にする——`connpass-api-v2-facts.md` は connpass-session-radar 側に
置いたまま参照する。取得段のペース制御・ページングのような部品は、**2本目が実際に要ると分かってから**
共通化を考える（`meta/architecture-selection.md`）。先に共通基盤を作らない。

## 6. 何を作らないか（初期スコープからの除外）

- **申し込み・キャンセルの自動化**。APIが存在しない
- **他人の履歴**。取得できるのは公開情報の範囲だが、他人を分析対象にしない
- **connpass以外のソース**（登壇、資格、業務経歴、書籍）。**将来入りうるが、最初は入れない**。
  connpassだけで地図が成立するかを先に確かめる
- **スクレイピング**。APIで取れないものはHTMLから取らない（規約で禁止）
- **他人への配信・購読**

**バックエンドを組むかどうかは未決事項に入れない。** 現時点では要らないと判断している——履歴は
多くても数百件で、集計はブラウザに全部載せて済む規模である。認証・他人のデータ・書き込みのどれかが
必要になった時点で、改めて判断する（P-02: 全体を先に設計しない）。

## 8. 受け入れの目安

- 自分の参加履歴が、時系列と分類の両方で読める形になっている
- 「今年何をやったか」と「どこが空白か」が、一覧を数えずに分かる
- 人に見せられる形を1つ持っている（公開の可否は §4 の結論に従う）
- APIキーがリポジトリに現れない
- connpassの1秒1リクエスト制限を超えない
- 履歴に載らない情報を推測で補っていない
