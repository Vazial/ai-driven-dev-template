# ADR-0001: 会議室予約システムの設計パックとしてドメインモデルパックを選定する

- 日付: 2026-07-13
- 状態: 承認済み
- 置き換え対象: なし

## 文脈

meta/architecture-selection.md の複雑度評価チェックリストに沿って、architectが会議室予約システムの特性を評価した。

| 評価軸 | 評価 |
|---|---|
| 不変条件の量 | 中〜多。例: 同一会議室・重複時間帯の二重予約禁止、開始<終了、定員超過禁止、キャンセル期限、部屋によっては承認要 |
| 状態遷移の複雑さ | 中。予約は 仮予約→確定→キャンセル／実施済み／不承認 のような複数状態を持ち、遷移条件が部屋種別・承認要否で変わる |
| ルールの変更頻度 | 高い想定。予約可能時間帯・承認フロー・キャンセルポリシーは組織の運用変更に追従して変わり続けやすい |
| CRUD比率 | 低〜中。作成・一覧・キャンセルは表面的にはCRUDだが、重複判定・状態遷移・承認フローという非自明ロジックが中心 |
| 連携中心か計算中心か | 計算中心。初期スコープでは外部カレンダー等の連携は含まない |
| データ特性 | バッチ・ストリーム処理なし。トランザクショナルなデータ操作のみ |

評価の裏付けとして、人間から既存のDDDモデリングワークの成果サマリー（docs/workshop-summary-01-reservation.md）の共有を受けた。そこでは「室×時間帯の排他的占有」を中核とする複数の不変条件、仮予約なしでも状態導出・キャンセル期限を含む状態モデル、並行制御2層（楽観ロック+DB部分排他制約）といった、不変条件・状態遷移中心の設計判断がADR8本として既に確定しており、本評価と整合する。

なお、ワーク側のADR 0001〜0008はドメイン設計の決定であり、本リポジトリのADR採番（本ファイルがADR-0001）とは別系列。ワーク側ADRの全文と受け入れシナリオ（reservation-create.feature / reservation-cancel.feature）の取り込みは未了で、契約ドラフト時の入力として人間に共有を依頼する。

## 決定

**ドメインモデルパック**を採用する。不変条件・状態遷移が多く、ルールが変わり続ける業務システムに適するパック（architecture-selection.md 4節）。

- 戦術的パターン（集約・値オブジェクト・ドメインサービス等）で予約の不変条件と状態遷移を表現する
- 構造検証（L2）を厳格化し、ドメイン層が技術詳細（永続化・HTTP等）に依存しないよう依存制約を敷く
- 具体的な言語・フレームワーク、ディレクトリ構成規約、依存制約ルールは、本ADR承認後に別ADRまたはARCHITECTURE.mdで確定する

## 検討した代替案

- 案A: シンプルCRUDパック / 不採用の理由: 重複判定・状態遷移・承認フローという業務ロジックの複雑さをTransaction Scriptで扱うと、ルール変更のたびに分岐が散らばり変更コストが増大する
- 案B: パイプラインパック / 不採用の理由: 本システムはバッチ・ストリーム処理やデータ変換連携が主戦場ではない
- 案C: フロント主体パック / 不採用の理由: ロジックの大半は予約可否判定というサーバ側業務ルールであり、UI側にロジックが集中する構成ではない

## 帰結

- 良い影響: 不変条件・状態遷移をドメイン層に凝集でき、ルール変更時の影響範囲を限定できる
- トレードオフ: シンプルCRUDパックに比べ初期の設計・実装コストが高い。CRUD比率の高い周辺機能（会議室マスタ管理等）まで同じ厳格さを適用すると過剰設計になりうるため、範囲は都度見極める
- 波及する作業: L2構造検証ルールの具体化、ディレクトリ構成規約の確定、design.mdへの反映（いずれもarchitectが本ADR承認後に着手）
