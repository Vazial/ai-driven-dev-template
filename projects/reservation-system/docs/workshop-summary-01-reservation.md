# ワークサマリー #1：会議室予約システム（DDD モデリング）

期間が空いても全体を思い出せるように、1問目のワークの成果を1枚に集約したもの。

---

## このワークで何をやったか

「複雑ドメインは向いてないかも／定型化したい」という出発点から、**直感ではなく繰り返せる手順**で、会議室予約ドメインの設計をゼロから机上で組み上げた。EventStorming → 集約設計 → 並行性 → ORM/CQRS → 制限ルールの見分け → 状態モデル、と進み、設計判断を ADR 8本＋受け入れシナリオ2本に落とした。

**到達点**：集約境界・並行制御・状態モデルまで自力で判断できるようになり、実装（Claude Code）に渡す直前まで完成。

---

## ドメインの骨格（EventStorming の結果）

- 鎖は2本＋分岐：
  - `予約する（社員）` → 予約が作成された ／ ↘ 予約が拒否された（不変条件違反）
  - `予約をキャンセルする（社員）` → 予約がキャンセルされた
- 「空き枠を確認する」はクエリ＝イベントではない → 読み取りモデルへ

## 確定した不変条件

- **中核**：室×時間帯の排他的占有（同室で時間帯が重なる予約は不可。過去／未来を問わない）
- **予約単体（軽い）**：最小30分／日マタギ禁止／TimeSlot の妥当性（0分・逆転を弾く）
- **またぎ（ID参照・スナップショット）**：営業時間内（部屋ごと）／定員以内
- **状態**：キャンセルは開始15分前まで

---

## 主要な設計判断（ADR 8本）

| ADR | 決定の要点 |
|---|---|
| 0001 | 集約は小さい `Reservation`。ダブルブッキングの砦は DB 排他制約 |
| 0002 | 不変条件の実施場所は「DB制約 → 事前チェック → 集約見直し」の順 |
| 0003 | 制限ルールは「何を見れば判定できるか」で見分ける（認識が先、道具は後） |
| 0004 | 過去予約を許可。中核不変条件を「室×時間帯の排他的占有」に一本化 |
| 0005 | 全時間区間は半開 `[start, end)`。入力は XX:00、末尾を縮めない |
| 0006 | 営業時間・定員は予約時にスナップショット（EC の注文時価格と同型） |
| 0007 | 状態は導出（生データは時間帯＋`cancelledAt`）。規則は `ReservationStatus.of()` に一元化（SSOT） |
| 0008 | 並行制御は2層（`@Version`＋部分排他制約 `WHERE cancelled_at IS NULL`）。時刻は `Clock` 注入 |

## 特に大きかった気づき（思考の軌跡）

1. **「◯◯Manager」の正体は集約**だった ── 複数データの整合をまとめて守るものを、集約として定義し直す。
2. **大集約の罠** ── 「Roomに全予約を持たせる」は膨張・ロック詰まり。集約は小さく、整合はDB制約へ。
3. **version は「不変条件を所有する集約」に置く** ── 並行制御は集約境界の問いの再登場。
4. **CQRS で旧スキルが活きる** ── 書き＝集約で整合、読み＝旧来の"使われ方からDB"を全開に。
5. **「数える／またぐ／状態」で見分ける** ── ルール追加時に集約を反射的に増やさない。
6. **「何を見れば判定できるか」が幹** ── 定員チェックは「他の予約を見ない」＝消せる軽いまたぎ。認識を誤ると重い道具を無駄使いする。
7. **状態の導出 vs 実データはトレードオフの移動** ── 身軽さの代償は「規則を1箇所に保つ規律（SSOT）」。トレードオフは消えず形を変える。
8. **過去枠禁止は不変条件ではなく登録ポリシーだった** ── ルールを症状でなく原理で名付け直すと、中核が一本化された。
