## 鳥瞰図

REST API 1本のシンプルなサーバアプリケーション（Java + Spring Boot + JPA、ADR-0002）。
中心に小さい`Reservation`集約を持ち、業務ルールはdomainに、ダブルブッキング防止の最終防衛はDB排他制約に置く。

```
[クライアント] → adapter/api → application → domain
                                    ↓
                          adapter/persistence → PostgreSQL(排他制約)
```

## モジュールの責務

| モジュール | 責務 | しないこと |
|---|---|---|
| domain | 予約の業務ルール（時間帯の妥当性・営業時間・定員）を判定する | Spring/JPA/HTTPを知らない |
| application | ユースケースの手順（部屋取得→予約生成→保存）を組み立てる | 業務ルールの判定そのもの |
| adapter/api | HTTPの受付と、契約（reservation-api.yaml）の形への詰め替え | 業務判断 |
| adapter/persistence | 永続化と、DB制約違反の業務エラーへの翻訳 | 業務判断 |

## 境界の意図

- domainをフレームワーク非依存に保つのは、業務ルールの単体テスト（L1）とmutation testingを高速・安定にするため
- 依存方向 `adapter → application → domain` の一方通行はArchUnit（L2）が強制する。ここには意図だけを書く
- 受け入れテスト（steps/dsl）は実装から隔離された別ソースセット。testerが実装コンテキストなしで書くため

## 用語集（ユビキタス言語）

| 用語 | 意味 | コード上の対応 |
|---|---|---|
| 予約者 | 予約する人。社員に限定しない | reserverId |
| 会議室 | 予約対象の部屋。営業時間と定員を持つ | Room |
| 時間帯 | 同じ日の中の開始〜終了。終了時刻は含まない（半開区間） | TimeSlot |
| 占有 | ある会議室のある時間帯が一つの予約に取られている状態 | DB排他制約 + 事前チェック |
| スナップショット | 予約時点の営業時間・定員の写し。後から部屋設定が変わっても予約は不変 | Reservation内の複製列 |

## 主要な流れ

予約作成（スライスRSV-C）: `POST /reservations` → api（詰め替え）→ application（部屋取得・予約生成）→ domain（ルール判定）→ persistence（INSERT、排他制約が最終防衛）→ 201 または 409/422+理由コード。
詳細な骨格は design.md、判断の経緯は adr/ を参照。
