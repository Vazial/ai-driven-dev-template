# verification.md — 多段保証モデル

> 対象: developer / reviewer、およびCI設計。
> 原則の根拠: P-01, P-10

## 1. モデルの構造

保証は5つの段の積層である。**下の段から順に失敗を濾し取り、上に行くほど人間に近づく**。
各段は「答える問い」で定義される。バックエンド/フロントエンドの違いは段の構造ではなく、各段の中の手段の違いにすぎない。

```
L5  体験の質          ←────────── 人間（唯一の聖域）
L4  仕様の充足        ←── 機械実行 + step実装の人間承認
L3  境界の整合        ←── 機械
L2  構造の健全性      ←── 機械
L1  実装の内部品質    ←── 機械
```

## 2. 各段の定義

### L1 — 実装の内部品質
- 問い: **コードは書いた通りに動くか**
- 手段: 単体テスト（JUnit / Vitest等）、lint、フォーマッタ
- 確定: 機械（カバレッジ基準 + **mutation testing**）

#### mutation testingを置く理由
単体テストは実装したdeveloper自身が書くため、「CIを緑にするための緩いテスト」が構造上ありうる。
mutation testing（PIT / Stryker等）は実装に変異を入れてテストが落ちるかを確かめ、何も検証していないテストを機械的に検出する。
テストの質の番人をagentや人間ではなく機械に担わせる（P-01, P-04）。

### L2 — 構造の健全性
- 問い: **変更に耐える形を保っているか**
- 手段: 静的構造検証（ArchUnit等）、依存関係lint（dependency-cruiser、ESLint境界ルール等）
- 確定: 機械（ルールは設計パックが定義する）

### L3 — 境界の整合
- 問い: **部品同士は噛み合うか**
- 手段: API仕様からの型・クライアント自動生成、契約テスト、DBスキーマとの整合検証
- 確定: 機械（仕様自体の承認はL4以前に契約として完了している）

### L4 — 仕様の充足
- 問い: **約束した振る舞いを満たすか**
- 手段: 受け入れシナリオの実行、E2Eテスト（主要フローに限定）
- 確定: 機械実行 + **step実装の人間承認**

#### なぜstep実装だけ人間の承認が必要か
シナリオ本文が正しくても、step定義（シナリオ→コードの翻訳）が誤訳されていたら、L4より下の全ての緑が無意味になる。保証の連鎖の要がここにある。
逆にstep定義さえ正しければ「シナリオが通る＝仕様を満たす」が成立し、人間が読む範囲をこの一点に圧縮できる。

#### L4詳細(1): レビューしやすい構造を先に強制する

step実装は4層に分離する（受け入れテストの層分離パターン）:

```
シナリオ本文     業務の言葉のみ。技術用語禁止
   │              例: 「会議室Aを10時に予約する」
   ▼
step定義        シナリオの文とテストDSLの対応付け「だけ」を行う薄い糊
   │              例: この文が来たら createReservation("会議室A", "10:00") を呼ぶ
   ▼
テストDSL       業務操作を関数化したテスト専用の共通ライブラリ
   │              例: createReservation() の中身が POST /reservations を組み立てて送る
   ▼
SUT             検証対象のシステム本体
```

用語:
- **テストDSL** (Domain Specific Language): 「予約を作成する」「在庫を引き当てる」のような業務操作を、業務の名前のまま関数にしたテスト専用ライブラリ。HTTP呼び出しやUI操作の技術詳細をこの層に閉じ込めることで、個々のstep定義に技術詳細が漏れるのを防ぐ
- **SUT** (System Under Test): 検証対象のシステム本体。受け入れテストはSUTの内部に触らず、外部から公開境界（API/UI）越しに操作する

**作成の分担**: step定義とテストDSLは、実装を書くdeveloperではなく**tester agentが作成する**。実装コードのコンテキストを持たないagentが翻訳を書くことで、「実装の内部をなぞって通るように書かれたテスト」を構造的に防ぐ。作成と監査の分離はagents.mdを参照。

step定義の規約（可能な限りlintで機械強制する。P-04）:
- **分岐・ループ・例外握りつぶし禁止**。step定義に条件が要る時点でシナリオ側の欠陥
- 1 step定義 = DSL呼び出し + 検証のみ。行数上限を設ける（目安: 10行）
- 状態の準備・検証はSUTの**公開境界**（API/UI）経由で行う。DB直接操作はGiven専用のseamとして明示的に定義した箇所のみ許可
- **既存stepの再利用を優先**。同義の新規stepを作らない（step一覧を自動生成し、類似検出をreviewerの監査項目にする）

#### L4詳細(2): 承認の運用

- 承認対象は「**新規・変更されたstep定義とDSL」の差分のみ**。承認済みstepの再利用はレビュー不要
  → step語彙が安定するほど承認コストは逓減する（初期スライスに集中投資する構造）
- 強制手段: `steps/`・`dsl/`ディレクトリにCODEOWNERSを設定し、人間の承認なしにマージ不能にする（P-04）
- 承認依頼には**対訳表**を添付する: 各stepについて「シナリオ文 → このコードが実際に行うこと（平易な文で）」の対応。対訳表は**step定義を書いたtesterではなく、reviewer agentがコードだけを読んで独立に作成する**（誤解の自己申告を防ぐ。agents.md参照）。人間はまずシナリオと対訳表を突き合わせ、疑わしい行だけコードに潜る

#### L4詳細(3): レビューチェックリスト

1. **過不足**: stepは文が言っている通りのことをしているか。文にない副作用・文にある条件の省略はないか
2. **Givenの正当性**: 前提状態を正しく作っているか。実装の内部をなぞって「通るように」準備していないか
3. **Thenの検証対象**: 業務上の結果を検証しているか。実装の内部構造（テーブルの中身等）に依存していないか
4. **失敗の握りつぶし**: 空catch、緩すぎる比較、sleep頼みの同期、リトライによる誤魔化しがないか
5. **暗黙の前提**: マジックナンバーや暗黙の仮定が、シナリオ側に明文化されているか

### L5 — 体験の質
- 問い: **人間にとって良いか**
- 手段:
  - Visual Regression Testing（スナップショット比較。ベースラインの初回承認のみ人間）
  - ブラウザ操作エージェント（Playwright MCP等）によるAI自身の操作・確認
- 確定: **人間**。「使い心地」の最終判断は機械化しない

## 3. 運用原則

### 3.1 失敗は下に押し込む（P-10）
上の段（特に人間）で見つかった失敗は、下の段の検証を強化する材料として扱う。
- 例: L5で人間が「仕様と違う」と気づいた → L4のシナリオ不足。シナリオを追加する
- 例: L4で受け入れテストが落ちる実装ミスが頻発 → L1/L2のテスト・ルール不足。そちらを足す
- 強化の記録はfriction logに残す

### 3.2 人間が手を出したら設計不足のサイン（P-01）
確定が「機械」の段に人間が介入し始めたら、その段の検証設計を直す。人間の関与を増やして対処しない。

### 3.3 CIの実行順序
L1 → L2 → L3 → L4 の順に実行し、下の段で落ちたら上の段は実行しない。全て緑でなければマージ不可。

## 4. 段×手段の対応表（リファレンス）

| 段 | バックエンド | フロントエンド |
|---|---|---|
| L1 | 単体テスト、lint | 単体テスト、lint |
| L2 | 静的構造検証 | 依存関係lint、境界ルール |
| L3 | API仕様→サーバ型生成、契約テスト | 同一API仕様→クライアント/型生成 |
| L4 | 受け入れシナリオ実行 | E2E（主要フローのみ） |
| L5 | —（対象外） | VRT、ブラウザ操作agent、人間の最終判断 |
