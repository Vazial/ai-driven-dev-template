# ADR-0024: 利用者の操作自由度(control surface)を明示し、断面②にユースケース走破を加える

> **承認者向けサマリ**: reservation-frontendのRFE-B(予約)実装で、空き帯(availability帯)をクリック
> すると、利用者が開始・終了時刻を指定できないまま帯全体(例: 9時間)が丸ごと予約される欠陥が生じ、
> 人間の実機レビューでのみ発覚した(修正済み)。原因は「シナリオの未定義部分をAIが不当に埋めた」ことでは
> なく、**表示方法を正当な理由で変更した際に、利用者が本来指定できるべき操作(開始・長さ)が黙って
> 失われ、それをシナリオ・テスト・骨格凍結(ADR-0021)のいずれも検知できなかった**ことにある。
> 人間は次の2点の制度化を決定した(再検討不要):
> **(A)** UIを持つプロジェクトの受け入れシナリオに、そのユースケースで利用者が指定できねばならない
> もの(control surface。例: 会議室/日付/開始/終了(または長さ)/人数)を明示し、断面②の検証で各項目が
> 実際に操作可能かを確認する。
> **(C)** 断面②の検証に、実機でユースケースの目的を通しで達成できるかを試す「ユースケース走破」を
> 加える(ブラウザ操作ツールを持つorchestratorが実施し、最終判断は人間が行う)。
> **コスト方針としてツールは作らない**——規約と検証手順の追加に留め、VRT等の自動化は今回採らない。
> ADR-0021(骨格凍結)は取り下げず、その限界(構造は守るが、インタラクションの意味・操作自由度は
> 守らない)を本ADRが補完する関係として明記する。承認いただきたいのは(A)(C)の制度化そのものと、
> 適用範囲(以後の新規シナリオに適用し、既存シナリオへの遡及適用はしない)である。

## 文脈

### 1. 何が起きたか

reservation-frontendの予約スライス(RFE-B)の実装で、**利用者が予約の開始・終了時刻を指定できない**
という欠陥が生じた。空き状況画面で空き帯(例: "09:00"から"18:00"の帯)をクリックすると、その帯全体
(9時間)がそのまま1件の予約として作成された。人間の実機レビューで発覚し、修正済みである。

designerが承認済みの外部AIモック(`projects/reservation-frontend/src/design-preview/BookingDesign.tsx`)
は、これとは異なる操作モデルを定義していた。タイムラインは30分単位のセルで構成され、セルの`onClick`
が**利用者による開始時刻の選択**を意味し、予約ダイアログは「クリックしたセルの時刻を開始時刻」
「長さはクイック予約として固定(実装は開始+1時間で`endTime`を計算する、`handleBook`関数)」という
形で開始・長さの両方を利用者の操作(セルクリック)経由で決めていた。すなわちモックは「セル=開始時刻の
指定、長さは固定」という**具体的な操作自由度**を持っていた。

一方、実装は案B(認証なし・情報公開範囲を絞る、`projects/reservation-frontend/adr/0006`)採用後、
availability APIが「空き帯」(始点と終点を持つ連続区間)を返す契約になっていることを踏まえ、表示を
「30分セルの列」ではなく「空き帯そのものを1つの矩形として描く」形に変更した。空き帯のAPI形状に
素直に従う自然な選択であり、**表示モデルの変更それ自体は正当**である。しかしこの変更に伴い、
「利用者が帯のどこをクリックしても、その帯全体が予約される」という実装になり、**利用者が開始・
終了(または長さ)を指定するという操作自由度が、誰にも気づかれないまま失われた**。

### 2. 正確な原因(「埋めた」のではなく「落ちた」)

この欠陥の原因を「シナリオが操作の詳細を定義していなかったので、AIが未定義部分を(誤って)埋めた」
と理解するのは不正確である。実際に起きたことは、**表示モデルの変更という正当な設計判断が、それに
伴う操作モデルの再導出を欠いたまま行われた**ことである。

- 表示モデルの変更(セル単位→帯単位の描画)は、availability APIの形状・案B採用という既存決定に
  照らして自然かつ正当な判断だった
- しかしこの変更は「セルをクリックする」という操作の意味(=開始時刻の選択)を暗黙に前提にしていた
  モックの操作モデルと衝突する。表示を変えるなら、利用者が何を指定できるべきかを**改めて問い直す
  必要があった**が、それが行われなかった
- 結果、構造(コンポーネント構成)は保たれたまま、**利用者の操作自由度だけが silently 失われた**

### 3. なぜどの既存の層も検知できなかったか

| 層 | なぜ検知できなかったか |
|---|---|
| 受け入れシナリオ(`.feature`) | 粒度を意図的に抽象化しており、操作自由度そのものを制約する記述を持たなかった(例: RFE-Aは「空き状況を確認する」という閲覧行為のみを扱い、予約作成の操作自由度には触れていない。RFE-Bも同様の抽象度で書かれていた) |
| step定義・テスト(tester) | 同じシナリオから同じagentが書いたため、シナリオが持つ抽象化(=操作自由度への無関心)がテストにもそのまま転写された。**盲点を共有した** |
| 骨格凍結による改修ガバナンス(`meta/adr/0021`) | 凍結対象は「おおまかなコンポーネント構成(何が存在し、どう配置・階層化されているか)」であり、**インタラクションの意味・利用者の操作自由度は対象に含まれない**(0021 §2.3)。今回、タイムライン・予約ダイアログ等のコンポーネント構成自体は変わっておらず、骨格凍結の警報は正しく鳴らなかった。骨格を守ることと、操作の意味を守ることは別の軸である |
| 実機レビュー(人間) | **唯一、この欠陥を検知した層**。シナリオ・テスト・骨格比較のいずれも通過した後、人間が実際に予約を作成する操作を行って初めて発覚した |

この整理から導かれる結論: **既存の検証の階層(verification.md L1〜L5)・骨格凍結(0021)・2断面
(0022)は、いずれも「構造」「振る舞いの結果」を守る仕組みであり、「利用者が何を操作できるか」という
自由度そのものを守る層を持っていなかった**。本ADRはこの層を新設する。

## 決定

以下2点は人間確定であり、architectはこれを再導出・再検討しない(`meta/adr/0011`の精神)。

### A: 利用者の操作自由度(control surface)を受け入れシナリオに明示する

UIを持つプロジェクトの受け入れシナリオ(`.feature`)には、そのユースケースで**利用者が指定できねば
ならないもの**を、ヘッダのコメント節として列挙する。RFE-B(予約作成)であれば: 会議室 / 日付 /
開始 / 終了(または長さ) / 人数。

- 書き場所: 既存の「解釈ポイント」節(`projects/reservation-system/contracts/reservation-availability.feature`
  等で先例あり。ADR-0002の雛形自体には明文化されていないが、architectが継続的に用いてきた慣行)に
  並ぶ独立節として置く。節名は「**操作自由度(control surface)**」とする
- 中身は業務の言葉で列挙するのみでよく、Gherkinのステップとして書く必要はない(シナリオ本文の抽象度
  は変えない。P-02の「スライスに必要な分だけ書く」精神を尊重し、シナリオ自体を過度に具体化しない)
- **なぜこれで盲点の共有を断てるか**: シナリオ本文の粒度は今後も意図的に抽象的でありうる。しかし
  control surfaceの列挙は**具体的な項目のリスト**であり、断面②の検証(下記)で「列挙した各項目が
  実際に操作可能か」を機械的にではなく人手で(しかしチェックリストとして)確認できる。シナリオが
  抽象化していても、control surfaceは具体であるため、同じagentが同じ抽象化を共有しても検出可能になる
- 断面②の検証(`meta/adr/0022`が定める実装合意のゲート)に、「シナリオのThen照合」とは別に、
  「列挙したcontrol surfaceの各項目が実装で実際に操作可能か」の確認を追加する

### C: 断面②の検証にユースケース走破を加える

断面②(実装合意)の検証手順に、**実機でユースケースの目的を通しで達成できるかを試す「ユースケース
走破」**を加える。シナリオのThen照合(個々の受け入れシナリオが緑になること)とは別の層であり、
「複数のシナリオ・操作をまたいで、利用者が本来やりたいこと(例: 好きな時間だけ会議室を予約する)を
実際に最初から最後まで達成できるか」を確認する。

- **実施主体**: ブラウザ操作ツール(Playwright MCP等、`meta/verification.md` L5が既に手段として
  挙げている)を実際に持つのはorchestratorである(4agentはいずれもBash/ブラウザ操作ツールを持たない、
  `meta/agents.md`の役割定義)。したがって**走破はorchestratorが実施する**
- **最終判断**: 人間が行う(`meta/verification.md` L5「確定: 人間」の原則をそのまま踏襲する)。
  今回の欠陥も、この経路(人間が実機で操作して発見)で実際に捕まっている
- 走破のチェック対象は、Aで列挙したcontrol surfaceの各項目が実際に操作できるかを含む。両者(A・C)は
  独立した決定だが、実務上は「Aが検証項目を列挙し、Cがそれを含めて実機で確かめる」という補完関係
  にある

### コスト方針: 規約と検証手順に留め、ツールは作らない

**リーンに実施する**。上記A・Cはいずれも既存の役割定義・検証段(`meta/verification.md` L4/L5、
`meta/agents.md`)に対する**規約・手順の追加**であり、新規ツール・自動化基盤は作らない。

- Visual Regression Testing・専用の操作自由度検証ツールの新設は、本ADRでは**採らない**(過剰にしない)
- `meta/verification.md` L5は既に「ブラウザ操作エージェント(Playwright MCP等)によるAI自身の操作・
  確認」を手段として挙げている。本ADRはこれを**新設するのではなく、断面②の必須手順として明示的に
  位置づけ、実施主体(orchestrator)を明確化する**ことに徹する
- 機械検証で完結させられない理由: control surfaceが「実際に操作可能か」の判定、ユースケース走破の
  「目的を達成できたか」の判定はいずれも意味理解を要し、機械のパターンマッチでは代替できない
  (`meta/verification.md` L5「確定: 人間」と同じ理由)。ここに機械を無理に持ち込まない判断は、
  `meta/adr/0021`が「UIの劣化判定は人間の目視」としたのと同型である

### ADR-0021との関係(supersedeではなく補完)

`meta/adr/0021`はsupersedeしない。**骨格凍結の限界を、本ADRの文脈で明記する**:

- `meta/adr/0021`が守るのは**構造**(おおまかなコンポーネント構成=何が存在し、どう配置・階層化
  されているか)である。これは「1から作り直して劣化する」ことを防ぐための仕組みであり、機能は
  果たしている
- `meta/adr/0021`が守らないのは**インタラクションの意味・利用者の操作自由度**である。コンポーネント
  構成が同じでも、あるコンポーネントの`onClick`が「開始時刻を選ぶ」から「帯全体を予約する」に
  変わるような変化は、骨格凍結の警報対象に入らない。今回の欠陥はまさにこの隙間で起きた
- 本ADR(A・C)は、この隙間を埋める**別の層**として位置づく。0021は「構造が保たれているか」を、
  本ADRは「利用者の操作自由度が保たれているか(A)」「ユースケースの目的が達成できるか(C)」を、
  それぞれ別の観点で検証する。両者は補完関係にあり、上書きではない

### 適用範囲: 以後の新規シナリオから。既存シナリオへの遡及適用はしない

`projects/reservation-frontend/contracts/availability-view.feature`(RFE-A、承認待ち・main上)、
および今回欠陥が見つかったRFE-B(予約作成、未マージPR上)を含め、**既存シナリオへの遡及適用は今回
行わない**。本ADR承認後に新規に起こすシナリオ(control surfaceを持つべきユースケース)から適用する。
RFE-A/RFE-Bを次に触るタイミング(洗練・改修・再承認等)で、control surface節を追記するかは、その時の
判断に委ねる(本ADRでは決定しない)。

## 検討した代替案

- 案A: Visual Regression Testing(操作前後のスクリーンショット差分)を導入し、モックと実装の
  インタラクションを自動比較する / 不採用: `meta/adr/0021`が既に「ピクセル比較は洗練のたびに動き、
  字義通り運用すると警報が鳴りっぱなしになる」と結論づけている。操作自由度の欠落はピクセル差分として
  現れるとは限らない(今回の欠陥も、帯をクリックして予約ダイアログが開く見た目自体は正常だった)。
  過剰な自動化を避けるという人間確定のコスト方針にも反する
- 案B: control surfaceをAPI仕様側のスキーマ制約として機械検証する(例: リクエストボディの必須
  パラメータの網羅率を測る) / 不採用: 「利用者が実際にUIから指定できるか」はAPIスキーマの問題ではなく
  UIのインタラクションの問題であり、API仕様の機械検証では代替できない。将来、より強い自動化が必要に
  なった場合の再検討候補として記録するに留める(過剰な先回りをしない、P-05)
- 案C: ユースケース走破をtester/developerが行う / 不採用: tester/developerはいずれもブラウザ操作
  ツール(Bash等の実行手段)を持たない役割設計になっている(`meta/agents.md`)。ツールを持つのは
  orchestratorのみであり、実施主体をそこに合わせるのが実態に忠実(`meta/adr/0021`が(b)外部AI実行の
  実行主体をorchestratorに定めた判断と同型)
- 案D: `meta/adr/0021`をsupersedeし、骨格の定義自体に「インタラクションの意味」を含める形に書き換える
  / 不採用: 骨格凍結の目的(洗練=操作感・細かいUI・architectとの齟齬解消を止めない)と、操作自由度の
  保証という目的は別軸であり、無理に一体化すると骨格の定義が肥大化し、0021が防ごうとした「警報の
  鳴りっぱなし」を再び招きかねない。**別の層として補完する方が両者の目的を独立に保てる**
- 案E: 既存シナリオ(RFE-A・RFE-B)に遡及的にcontrol surface節を追加する / 不採用(今回時点): RFE-Bは
  未マージPR上にあり、RFE-Aは別のスライスとして承認待ちの状態にある。人間確定の指示により、遡及適用は
  今回のスコープに含めない。次にこれらのシナリオを触る際の判断に委ねる

  保つ(`meta/adr/0022`・`0023`の先例と同じ扱い)
- **`meta/templates/acceptance-scenario.feature`の「記入のコツ」に軽い追記を行う**: UIを持つプロジェクト
  の受け入れシナリオには、既存の「解釈ポイント」節に並ぶ形で「操作自由度(control surface)」節を

- **既存シナリオへの遡及適用はしない**。RFE-A(`availability-view.feature`)・RFE-B(未マージPR)は
  次に触る際の判断とする(上記「適用範囲」参照)
- **`meta/verification.md`は編集しない**: L5が既に「ブラウザ操作エージェントによるAI自身の操作・
  確認」を手段として挙げており、本ADRの決定(C)はこの既存記述と矛盾しない。実施主体の明確化・
  「断面②の必須手順への格上げ」は本ADR側の記述で足り、verification.md自体への追記は過剰と判断した
  (リーンに保つ、コスト方針)
- **`meta/adr/0021`は編集しない**(P-06)。本ADRとの関係(補完・supersedeでない)は本ADR側にのみ記す
