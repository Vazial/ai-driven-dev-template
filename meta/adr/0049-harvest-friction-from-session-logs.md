# ADR-0049: セッションログからfriction候補を収穫し、mainへのマージを収穫のトリガにする

> **承認者向けサマリ**: friction-log は「その場で書く」ことを前提に設計されている
> （`meta/adr/0012`・P-05）。だが実際には書き損ねる——**溜まったセッションログ149MB・28
> セッションを走査したところ、既知のFRに対応する摩擦が機械的に再発見できた**（`FR-002` の
> ブリーフ議論、`ADR-0040` になった `.env.example` の議論、施錠による `denied` エラーの
> 連発）。既知を拾えるということは、**未記録の分も同じ精度で拾える**ということである。
> **(1)** セッションログ（`~/.claude/projects/**/*.jsonl`）を friction-log の一次データの
> 取りこぼし回収先として正式に位置づける。**(2)** 走査は機械的シグナルのみで行い、意味の
> 判定はしない。**(3)** 出力は**候補であってFRではない**——`friction-log.md` への追記は
> 人間のGOのあとに行う。**(4)** トリガは `gh pr merge` の PostToolUse hook とし、閾値未満の
> ときは**何も出さない**（軽量な修正はここで黙って落ちる）。**(5)** 置き場を `meta/loop/` と
> する——`0046` の施錠は**ゲート**にかかるものであり、収穫ツールはゲートではない。この区別を
> 本ADRで明文化する。**(6)** 収穫位置の状態ファイルは各自の環境に属し、gitに入れない。
> **(7)** 効果の測定は**回帰検知に限る**——摩擦率のベースラインは **3.8%**（26回に1回、人間が
> 打ち直している）だが、**この流量では改善は測れず、大きな悪化だけが測れる**（半減の検出に
> 約7.5か月、2倍の悪化なら約3.6か月）。**測れないことを測れると言わない**。

## 文脈

### 0. このADRの起草者について（meta/adr/0047）

本ADRは orchestrator が起草した。`0047` 決定2 の目安——「そのADRの素材が『摩擦の観測』なら
orchestrator」——に当たる。素材は蓄積したセッションログそのものであり、走査と評価は
orchestrator が実行した。

### 1. friction-log の設計が前提していること

`meta/adr/0012` と P-05 は、frictionを**その場で**書くことを求めている。棚卸しでまとめて
書くと記憶で精度が落ちるからである。この前提は正しい。だが「その場で書かなかった分は
永久に失われる」という帰結までは意図していない。

`activeContext` は既に、記録が落ちた事実をいくつも抱えている。`orchestrator-as-substantive-
source` は「実質4回」だが機械はファイルごとにしか数えない。`RSV-L の監査が未実施` は
reviewer が独立に再発見するまで気づかれなかった。**記録は落ちる**。

### 2. 落ちた記録は、実は残っている

Claude Code は全セッションを `~/.claude/projects/<slug>/*.jsonl` に残す。このリポジトリの
分だけで **149MB・28セッション**（2026-07-13〜08-22）が溜まっていた。ここには人間の発話・
AIの応答・ツール呼び出しと結果・ブランチ名・時刻がすべて入っている。**一次データは捨てられて
いない。回収していないだけである。**

### 3. 実測——何が拾えて、何が精度を壊すか

走査を実装して28セッションに当てた。

**拾えたシグナル**（いずれも機械的に判定できるものだけ）:

| シグナル | 根拠 |
|---|---|
| 人間が打ち直した否定・訂正 | 人間が手で止めた＝AIが外れた証拠。最も強い |
| AI自身の自己訂正 | 直前に何かを誤っている |
| ツール実行の拒否・割り込み | 同上、より明示的 |
| 同一エラーの連発（4回以上） | 詰まっていた |
| 同一ファイルへの書き込みの往復（8回以上） | 迷っていた |

**精度を壊すもの**: `role: user` のレコードには、人間がタイプしていないものが大量に混ざる
——このリポジトリの実測で **task-notification が231件、人間の発話が522件**。これを外さずに
走らせた最初の実装では、候補の中身が**ほぼ全部 task-notification** になった。
`promptSource` フィールドは task-notification にも付くため判別に使えない（実測）。先頭の形
（`<`・`[Image:`・`Caveat:`・引き継ぎサマリ）と長さで落とす必要がある。

**スコアの分布に段差が出た**——ここが「軽量な修正を落とす」判断そのものである:

```
29, 25, 22, 19, 15, 15, 13, 8   ← 摩擦のあったスライス（8本。閾値8以上）
--------------------------------  ← 段差
 5, 5, 5, 4, 3, 3, 2, 2, 2, 0×11  ← 軽量・雑務のセッション（20本）
```

セッションの長さでは決まっていない（345ターンのセッションがスコア0）。シグナルの数で決まる。

**既知のFRを再発見できた**: `FR-002`（`narrow-brief-yields-weak-external-design`）になった
ブリーフ議論、`ADR-0040` になった `.env.example` の議論、`0046` の施錠による `denied` エラーの
連発。既知が拾えるということは、未記録の分も同じ精度で拾えるということである。

## 決定

**決定1. セッションログを friction-log の一次データの取りこぼし回収先として位置づける。**
「その場で書く」（P-05・`0012`）は依然として第一の手段であり、本ADRはそれを緩めない。収穫は
**書き損ねた分を拾い直すための第二の手段**である。

**決定2. 走査は機械的シグナルのみで行い、意味の判定はしない。** スコアは「人間が読む価値の
見込み」であって、frictionの重さではない。判別の要は**人間がタイプした発話とそれ以外の
切り分け**にあり、ここを外すと候補は無意味になる（文脈3の実測）。この判別ロジックには単体
テストを付ける（`meta/loop/test_harvest_friction.py`）。

**決定3. 出力は候補であってFRではない。** 収穫は「読むべき瞬間」を並べるだけで、
`friction-log.md` への追記は**人間のGOのあと**に行う。`meta/permissions.md` は friction-log を
AIの自律更新可としているが、**機械が拾った候補を機械が起票すると、誤検出がそのまま台帳に
残る**。cause_key の再利用判断（`0012`）も人間の目を要する。自律更新の対象は「AIが自分で
気づいて書く」場合に留める。

**決定4. トリガは `gh pr merge` の PostToolUse hook とする。** スライスがmainへ入る瞬間が、
振り返りの自然な区切りである。走査範囲は**前回の収穫以降**とし、閾値（既定8）未満のときは
**何も出さない**——軽量な修正はここで黙って落ち、収穫は摩擦のあったスライスにだけ反応する。

ただし hook の `if` フィルタ（`Bash(gh pr merge*)`）**だけに頼らない**。実測で、
**バッククォートで囲まれた文字列はコマンド置換として解析され `if` に一致する**ことが分かった
——クォート付き heredoc の中でも同じで、本ADRのコミットメッセージに `gh pr merge` と書いた
だけで hook が発火した。誤発火そのものは無害だが、**収穫位置が黙って進んで未収穫の蓄積を
食う**。したがって呼ばれた側でコマンド文字列を再検査し、一致しなければ収穫位置も進めない。

**決定5. 置き場を `meta/loop/` とし、`0046` の施錠との関係を明文化する。** `0046` が施錠した
のは「**何を正しいと判定するか**」——ゲートである。収穫ツールは何も失敗させず、何も判定
しない。したがってゲートではなく、施錠の対象ではない。`meta/tools/` に置くと `.claude/
settings.json` の `Write(./meta/tools/**)` deny により**閾値の調整のたびに人間の開錠を要する**
——`deny` は `allow` で上書きできず除外構文も無い（`0040`・`0046` の実測）。判定しない道具に
その手続を課す理由がない。

**決定6. 収穫位置の状態ファイル（`.claude/harvest-state.json`）はgitに入れない。** どこまで
走査したかは各自の環境に属する事実であり、共有すると意味を持たない（P-11の同型）。

**決定7. 効果の測定は「回帰検知」に限り、「ループが効いた」の証明には使わない。**
摩擦率（人間の訂正プロンプト ÷ 人間のプロンプト総数）を `meta/loop/friction_trend.py` で測る。
実測のベースラインは **3.8%（訂正17件／450件、2026-07-13〜08-22）**——およそ26回に1回、
人間が打ち直している。

**この指標で改善は証明できない。** 理由は2つあり、どちらも運用で消えない。

1. **交絡が畳めない**: モデルが変わる／タスクの性質が変わる（初期は規程が無いので摩擦が
   多くて当然）／人間の指示も上手くなる。摩擦率が下がってもループの寄与は切り出せない
2. **流量が足りない**: 週あたり約75プロンプト。両側5%・検出力80%で、半減の検出には片側
   1,207件（**約7.5か月**）、3割減なら片側3,789件（**約23か月**）を要する。一方で2倍の悪化は
   片側585件（**約3.6か月**）、3倍なら片側190件（**約1.2か月**）で捉えられる

つまり**改善は現実的な期間では測れず、大きな悪化だけが測れる**。週次の折れ線は読んでは
いけない（週あたりの訂正は1〜5件で、上下はノイズである）。ツールは判定に足る件数が貯まる
まで「まだ判定できない」と言い、あと何件要るかを示す。**測れないことを測れると言わない**の
がこの決定の本体である。

測定にあたっては `uuid` による重複排除が必須である。セッションはフォーク・再開で分岐し、
同じレコードが複数ファイルに入る（実測: 全レコードの**21.7%**）。潰さずに率を出すと、分岐の
多い週だけ分母が膨らんで**偽のトレンドが出る**。

## 帰結

- **得るもの**: 書き損ねた friction が失われなくなる。テンプレート改善の一次データの回収率が
  上がる。cause_key の再出現（`0012` のREPORT）が実データで裏打ちされる
- **払うもの**: 誤検出を人間が読み飛ばすコスト。閾値は実測の段差から8としたが、運用で調整する
  ——調整は施錠の外なのでAIが実施できる（決定5）
- **効かない範囲**: hook は Claude Code の機構であり、**Codex には届かない**（`activeContext`
  の留意事項）。Codexのセッションは別の形でログを残すため、本ADRの収穫はClaudeのセッションに
  限る。runtime横断で効かせたい規律は権限設定やhookではなく govlint に置く、という既存の原則は
  変わらない
- **やらないこと**: jsonl の削除・圧縮・ローテーション。溜まっていること自体は問題ではなく、
  回収していないことが問題だった（P-05: 要るようになってから）
