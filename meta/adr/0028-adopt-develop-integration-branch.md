# ADR-0028: developを統合ブランチとする二段階のブランチ運用を採用する

> **承認者向けサマリ**: 現在の「短命ブランチからmainへ直接PRする」運用を改め、`develop`を日々の
> 統合先、`main`をリリース可能な履歴とする。各スライスは`develop`から短命ブランチを切り、PRレビューと
> CIを通して`develop`へ統合する。`main`への反映は、`develop`からのPRを人間が承認・マージして行う。
> 開発途中の変更をmainから分離できる一方、ブランチが1本増えるため、二重のCIと統合タイミングの管理を
> 受け入れる。

## 文脈

guardrails.mdはtrunk-basedとして「1スライス=1短命ブランチ=1PR」「人間のみがmainへマージ」と定めている。
この構成は小さな変更をmainへ素早く反映するには適しているが、複数のスライスを並行させる間、リリース可能な
mainと開発中の統合状態を分けたいという要望が生じた。

開発中の統合先を明確にしつつ、PRレビュー・CI・人間による最終マージという既存の保証を維持するため、
ブランチの役割を再定義する必要がある。

## 決定

`develop`を長期の統合ブランチ、`main`をリリース可能なブランチとする。

1. 各スライスは最新の`develop`から短命ブランチを作成する。
2. スライスのPRは`develop`をbaseとし、承認対象・CI結果をPR上でレビューする。CIが緑で人間の必要な
   承認が揃った場合のみ`develop`へマージする。
3. `main`への反映は`develop`をheadとするPRで行う。人間がCI結果と統合差分を確認し、マージする。
4. `develop`と`main`の直接push、force push、ブランチ削除は禁止を維持する。ブランチ保護とCI必須チェックを
   両方のブランチへ適用する。
5. 既にmainをbaseとして作成済みのPRは、個別に`develop`へ移し替えず、人間がこの変更をマージした後に
   新規スライスから新運用を適用する。

## 検討した代替案

- 案A: trunk-basedを維持する / 不採用の理由: 開発中の統合状態とリリース可能なmainを分けたいという
  要求を満たせない。
- 案B: Git Flow全体（release・hotfix等を含む）を導入する / 不採用の理由: 現時点の規模には役割と
  ブランチが多すぎ、運用の複雑さが先行する。
- 案C: developを統合ブランチとする二段階の運用を採用する / 採用の理由: 短命ブランチとPRによる
  レビューを保ったまま、開発中の統合とmainへの昇格を分けられる。

## 帰結

- このPRには、Codex向けのAGENTS.md、guardrails.md、PRテンプレート、各CIワークフローの`develop`向け
  トリガーを同梱する。これらは本ADRと同じPRのマージで有効になる。
- `develop`の作成とGitHub ruleset設定はgit管理外のため、人間がmainから作成・設定する。AIはこのADRの
  承認・マージと設定完了を確認してから、スライス用ブランチのbaseとして利用する。
- mainへの統合頻度は固定しない。リリース可能なまとまりができた時点で、人間が`develop`からmainへの
  PRを作成・マージする。
