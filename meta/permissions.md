# permissions.md — 権限規程

> 対象: 全agent。成果物に触れる前に該当行を確認する。
> 原則の根拠: P-01, P-07, P-08

## 1. 権限マトリクス

全成果物の起案・執筆はAIが行う。区別するのは「人間がどう関与し、何をもって確定するか」。

| 成果物 | 人間の関与 | 確定条件 | 機械検証 |
|---|---|---|---|
| 契約（受け入れシナリオ・API仕様・ADR） | 意図を語る。ドラフトを承認する | **人間の承認** | スキーマlint |
| 設計骨格（モジュール境界・データモデル） | 提案を承認する | **人間の承認** | 構造検証 |
| 実装コード | 原則関与しない | テスト+lint通過 | フル |
| 単体テスト | 原則関与しない | カバレッジ基準+契約対応表 | フル |
| ビルド設定・検証ツール（build.gradle・govlint等） | **ゲート（判定ロジック）の変更時のみ承認**。AIから施錠されており、開錠は人間が行う（meta/adr/0046） | 開錠後、developerがテスト付きで実装する。施錠されていることをgovlintがERRORで検証する | フル |
| CIワークフロー（.github/workflows/） | **ゲート（必須チェック）の変更時のみ承認** | orchestratorが編集。ゲート変更は人間承認 | 自己検証（PRのCI） |
| 受け入れテストのstep実装 | 翻訳の正しさをレビューする | **人間の承認** | テスト実行 |
| 信条・規程（PRINCIPLES.md、本ファイル等） | ドラフトを承認する。変更はADR必須 | **人間の承認** | — |
| HANDOFF.md（不変のオンボーディング） | ドラフトを承認する。変更はADR必須 | **人間の承認** | — |
| activeContext.md・friction log | いつでも閲覧・上書きできる | **AIが自律更新可**（承認不要） | 形式lint |
| ARCHITECTURE.md（設計の現在） | PR差分で確認できる | **AIが自律更新可**。ただし承認済み決定の投影のみ。新規決定の持ち込み禁止 | — |
| design.md（現在の設計の地図） | 設計骨格の承認に随伴して確認する | architectが上書き維持（骨格自体の承認は済んでいる前提） | — |

人間の承認ポイント: **契約 / 設計骨格 / step実装 / 信条・規程の変更** の4箇所。
「ビルド設定・検証ツール」と「CIワークフロー」のゲート変更は**5つ目の承認ポイントではなく**、4つ目（信条・規程の変更）に含まれる——**何を正しいと判定するかを変えることは、規程を変えること**である（meta/adr/0046 決定2）。
各承認ポイントの成果物は、冒頭に承認者向けサマリを置く（結論・要点を平易な言葉で先頭に集約し、証跡・詳細は後続の節に分離する。meta/adr/0016）。

### 人間判断の記録ルール（meta/adr/0003）

設計骨格の承認以降に人間の判断（承認済み決定からの逸脱・契約の解釈の裁定・矛盾の解決）が発生したら、判断の大小を問わず**ADRを起票してから作業を再開する**。チャット上の承認だけで先に進まない。
friction-logへの記録は別判定: 人間判断の発生そのものはfrictionではない（エスカレーションは正常動作）。**AIの迷い・誤り・見逃しが関与した場合のみ**friction-logにも記録する。

### メモリ系ファイルの自律更新ルール
- 更新タイミング: スライスの区切り、エスカレーション発生時
- activeContext.mdは追記ではなく上書き（P-11）。friction logは追記のみ
- ARCHITECTURE.mdはarchitectが構造変更時に更新する。「設計の現在」を映す記述的な地図であり、ADR（判断の歴史）と対をなす
- AIが自律更新できるのはこの3ファイルのみ。信条・規程・契約への波及が必要だと判断した場合は、直接編集せず変更提案を出す

## 2. 人間に判断を仰ぐときの型（meta/adr/0051）

AIが人間に判断を仰ぐときは、次の4点を**揃えて**出す。人間が聞き返さなくても、その場で選べる状態にすること。

1. **決めること**を一文で（何が決まっていないから止まっているのか）
2. **選択肢**を具体的に。AIが把握している範囲で網羅する。「今は決めない／現状維持」が成立するなら、それも1つに数えて明示する
3. **各選択肢のトレードオフ**（何を得て何を失うか）
4. **推奨**（あれば。理由を添える）。ただし**命令にしない**——推すことと決めることは違う

**適用する**: 承認済み決定からの逸脱・契約の解釈の裁定・矛盾の解決（＝下記「人間判断の記録ルール」がADR起票を求める判断）に加え、方式の選定・スコープの取捨・優先順位・やる/やらないの判断。

**適用しない**: (i) **意図の聞き取り**——選択肢を並べるとAIが用意した枠の中にしか人間の意図が入らなくなる（P-07が守ろうとしている自由度）。開いた問いのままにする。(ii) **事実の確認**。(iii) **AIが自分で決めてよいこと**——判断依頼を増やすこと自体がP-01に反する。**選択肢が1つしかないなら、それは判断依頼ではなく報告である**。

chatでの提示の仕方は成果物に残らないため機械検証しない（P-04のできない側）。判断がADRになるときは、提示した選択肢と却下されたものが `approved_by` か `検討した代替案` 節のどちらかに残る。

## 3. エスカレーションプロトコル（§2の特殊例）

AIが契約を満たせないと判断した場合:

1. **実装を止める**。仮定で突き進まない。契約を書き換えない
2. **矛盾分析レポートを提出する**
   - どのシナリオとどの制約が衝突しているか
   - 修正案A/B（それぞれのトレードオフ付き）
3. **人間が判断する**。契約側を直す場合はADRを1枚追加（なぜ契約が間違っていたかの記録）
4. **AIが再開する**

契約の変更提案はIssue/コメントとして出す。AIによる契約ファイルの直接変更は禁止。

## 4. 矛盾分析レポートの型

```
## 矛盾分析: <スライスID>
- 衝突: <シナリオ/制約X> と <シナリオ/制約Y>
- 事象: <何を実装しようとして何が成立しなかったか>
- 案A: <内容> / トレードオフ: <...>
- 案B: <内容> / トレードオフ: <...>
- 推奨: <A or B> / 理由: <...>
```
