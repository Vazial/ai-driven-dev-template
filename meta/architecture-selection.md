# architecture-selection.md — 設計パック選定規程

> 対象: プロジェクト開始時のarchitect、および人間。
> 原則の根拠: P-09

## 1. 目的

アーキテクチャスタイルに汎用解はない。複雑度に対して過剰な設計は開発コストを、過少な設計は変更コストを膨張させる。
プロジェクト開始時に複雑度を評価し、B層の設計パックから適合するものを選ぶ。

## 2. 選定の流れ

1. AIが下記チェックリストに沿ってプロジェクトの特性を評価し、パックを提案する
2. 人間が承認する
3. 選定理由を**ADR第1号**として記録する（後からパックを乗り換える場合の判断材料になる）

## 3. 複雑度評価チェックリスト

| 評価軸 | 見るもの |
|---|---|
| 不変条件の量 | 「同時にXであってはならない」「合計がYを超えてはならない」のような業務ルールの数 |
| 状態遷移の複雑さ | 状態の数と、遷移に条件が絡む度合い |
| ルールの変更頻度 | 業務ルールが今後も変わり続けるか、一度作れば安定するか |
| CRUD比率 | 処理の大半が単純な登録・参照・更新か |
| 連携中心か計算中心か | 外部システムの橋渡しが主か、独自の業務ロジックが主か |
| データ特性 | 大量データのバッチ・ストリーム処理が主戦場か |

## 4. 設計パックの例

| パック | 適するケース | 主な構成 |
|---|---|---|
| シンプルCRUDパック | CRUD比率が高く不変条件が少ない管理画面・社内ツール | Transaction Script、薄いサービス層、生成系ツール活用 |
| 軽量ドメインモデルパック | 不変条件・状態遷移は多いが、連携面が小さく永続化技術が単一の中複雑度システム | 値オブジェクト・集約・DB制約は維持し、層を圧縮（ポート/アダプタ分離とドメイン/ORM二重表現を省略）。構造検証は「ルールの置き場」に絞る（meta/adr/0005） |
| ドメインモデルパック | 不変条件・状態遷移が多く、ルールが変わり続け、境界の交換可能性も要る業務システム | 戦術的パターン（DDD等）+ヘキサゴナル、構造検証を厳格化 |
| パイプラインパック | データ変換・バッチ・連携が主 | 関数的なステージ構成、入出力スキーマ検証中心 |
| フロント主体パック | ロジックの大半がUIにあるツール・可視化 | コンポーネント設計規約、状態管理規約中心 |

## 5. 全パック共通の必須部品

どのパックも以下を同じ形式で提供する（A層の規約に従う）:

- ディレクトリ構成規約
- 構造検証ルール（そのパックにおける「やってはいけない依存」の定義 → verification.md L2）
- テスト戦略（何をどの段でどこまでテストするか → verification.md）
- CLAUDE.md断片（そのパック固有の規約）
