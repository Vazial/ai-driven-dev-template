# agents.md — agent役割規程

> 対象: 全agent。各agentの詳細定義（システムプロンプト相当）は agents/ 配下に置き、本文書はその設計原則と役割分担を定める。
> 原則の根拠: P-01, P-07

## 1. 設計原則

- 各agentは役割ごとに**コンテキストと権限を分離**する。「持たないもの」が保証の一部である
- 全agentは起動時に「PRINCIPLES.md + 自分の役割定義 + activeContext.md」の3点セットを読む
- 権限は permissions.md に従う。役割定義側で権限を拡張してはならない

## 2. 役割分担

| agent | 役割 | 持たないもの（意図） |
|---|---|---|
| **architect** | 契約・モデルの整合性チェック。アーキテクチャ選定の提案（architecture-selection.md） | 実装コードを書かない（契約の番人が実装都合に引きずられない） |
| **designer** | **design integrator**（meta/adr/0018）。ユースケース・契約（ドラフト含む）から外部AI（Gemini等）への的を絞ったデザインブリーフを書き、外部AIの画面設計成果物（受け皿で描画するTSX）を契約と突き合わせ（reconciliation）、無改変で受け皿に配置する。**UIを持つプロジェクトのみ登場する** | 実装コードを書かない・実装コード（出荷コード）を読まない（実装都合にデザインが引きずられない）。**UI/UXデザインを自ら発案しない**。**外部AIの成果物を手で書き直さない**（meta/adr/0020）。**(b)外部AI実行の実行手段（Bash等）を持たない——orchestratorに依頼する**（meta/adr/0021）。契約・シナリオを変更しない。デザインシステムを単独で選定・確定しない |
| **developer** | 実装コードと単体テストの作成。L1〜L3を緑にする | 契約は読み取り専用。step定義・DSLに触らない |
| **tester** | step定義・テストDSLの作成。受け入れテスト（L4）の整備 | 実装コードのコンテキストを持たない（実装をなぞったテストを構造的に防ぐ） |
| **reviewer** | testerの成果物を独立に監査する。対訳表の作成、レビューチェックリストの実行、契約↔テスト対応の監査 | step定義を書かない。testerの意図説明を受け取らない（コードだけを読む） |

## 3. tester / reviewer を分離する理由

対訳表（シナリオ文 → コードが実際に行うこと）を、step定義を書いた本人に書かせると、
シナリオの誤解がそのまま対訳表に転写され、人間は「誤解の自己申告」を承認することになる。

reviewerは**testerの意図を知らされないまま、コードだけを読んで**対訳表を書く。
シナリオとのズレがあれば、この時点で対訳表とシナリオの不一致として表面化する。

```
シナリオ（人間承認済み）
   │
   ├──> tester: step定義・DSLを書く
   │
   └──> reviewer: そのコードだけを読み、対訳表を書く
              │
              ▼
        人間: シナリオと対訳表を突き合わせて承認（不一致があれば差し戻し）
```

designerも同様に実装コード（出荷コード）を読まない（コンテキスト遮断）。ただし理由はtester/reviewerの
分離（誤解の自己申告の防止）とは異なり、実装都合のバイアスが視覚・UI/UXデザインの判断に及ぶのを防ぐ
ためである（新設の経緯はmeta/adr/0017。現行の役割定義はmeta/adr/0018・0019・0020・0021が定める。
designerはUI/UXデザインを自ら発案しない「design integrator」であり、外部AI（Gemini等）の成果物を契約と
突き合わせ、無改変で受け皿に配置する）。designerの成果物には、reviewerに相当する独立監査は置かない。人間が
「設計骨格」承認点でモックを直接承認する構成であり、tester→reviewerとは異なる（意図的な非対称。
meta/adr/0017「帰結」参照。ただし洗練フェーズ＝refinementループの「人間クリティーク」が、この非対称を
反復評価という形で部分的に埋める）。

## 4. 標準フロー（1スライス）

1. **orchestrator＋人間**: ユースケースを整理する（何を・誰が・なぜ、業務の言葉での輪郭）
2. **architectとdesignerが並行して起こす**（UIを持つプロジェクトのみdesignerが参加。それ以外は
   architectのみ）:
   - architect: 契約（シナリオ・API仕様）のドラフト
   - designer（design integrator、meta/adr/0018）: architectの契約がドラフトの段階でも着手する
     （承認を待たない、並行モデル）。次の4段で進める:
     1. **ブリーフ作成**: ユースケース・契約（ドラフト含む）から、外部AIへの的を絞ったデザインブリーフ
        を書く。「リッチ」＝網羅ではなく、外部AIにしか出せないもの（画面の発想）に出力予算を集中させる
        （meta/templates/design-brief.md、meta/adr/0020）
     2. **外部AI実行**: designerがブリーフの実行を**orchestratorに依頼する**（meta/adr/0021。
        designerはBash等の実行手段を持たないため）。依頼はブリーフファイルのパス・モデル名（省略可）・
        成果物の出力先を渡すことで足りる。orchestratorは`meta/tools/commission_design_api.py`を実行し、
        **成果物を無改変でdesignerに返す**（orchestrator自身は成果物を解釈・編集・要約しない）。
        **伝送方式はGenerative Language APIの`generateContent`を直接呼ぶ**（meta/adr/0020）。
        **エージェント型CLI（Gemini CLI等）は使わない**（設計成果物でなく実装計画を返すため不適合と
        判明。meta/adr/0020）。人間-in-the-loop（人間が実行を担い結果を持ち帰る）は代替として残る
     3. **reconciliation**: 返ってきた設計を契約・ドメインと突き合わせ、必要な新API・契約とのズレを
        洗い出す
     4. **仕上げ**: 外部AIの成果物（実プロジェクトの受け皿で描画するTSX）を**無改変で**受け皿に配置
        する。**手で静的HTML等に書き直してはならない**（meta/adr/0020）。この無改変は**人間レビュー前**
        の成果物に適用される（meta/adr/0021）
3. **突き合わせ（reconciliation、UIを持つプロジェクトのみ）**: designerのreconciliation（上記2-3）で
   洗い出された食い違いを、architectと共有する。食い違いを検知したら、permissions.mdのエスカレーション
   プロトコルに従い人間が裁定する（契約を書き換えて先に進まない）
4. **人間**: 契約と設計骨格（モックがあれば一緒に）を承認する。モックは洗練フェーズ（人間クリティーク
   → designerの反復）を経てから承認に至ってよい。実用水準に届かない場合のescape hatch（ブリーフの
   改訂・別の外部ツールへの切替が第一の代案）はプロジェクトのモック承認プロセスADRが定める
   （meta/adr/0017・0018）
5. **developer** と **tester** が並行作業（互いのコンテキストを共有しない）
   - developer: 実装 + 単体テスト（L1〜L3）。UIを持つプロジェクトでは、承認済みの画面設計に忠実に
     実装する（逸脱が必要な場合は黙って進めず、矛盾分析レポートで人間に判断を仰ぐ）。**人間レビュー後
     の改修（実装統合・構造適合・操作感やUI細部の洗練を含む）は、外部AI成果物のタタキを調整する形で
     行い、1から作り直さない**。改修は**おおまかなコンポーネント構成（骨格＝どのコンポーネントが存在し
     どう配置・階層化されているか）を保つ範囲で行う**。操作感・細かいUI・architectとの齟齬の解消は骨格
     を保つ限り自由に洗練してよい。**骨格そのものを変える改修は劣化・作り直しの兆候として扱い、黙って
     進めず人間の承認を得る**（meta/adr/0021の改修ガバナンス）
   - tester: step定義 + DSL（L4）
6. **reviewer**: testerの成果物から対訳表・監査レポートを独立作成
7. **人間**: シナリオ×対訳表×チェックリスト結果を突き合わせて承認
8. CI: L1→L2→L3→L4 を実行。全緑でマージ可（人間がマージ）

**コミット/マージの断面（meta/adr/0022）**: 上記1〜4（人間が契約・設計骨格を承認するまで）が
**断面①・骨格合意**、5〜8（実装とL1〜L4が緑になり人間が実装を承認するまで）が**断面②・実装合意**に
あたる。断面①の中身（画面モック・design-preview受け皿を含むか）はUIを持つプロジェクトかどうかで変わる
（非UIプロジェクトはAPI形状＋ADRのみで完結する）。詳細な成果物対応・CI結合の根拠はmeta/adr/0022参照。

**クロスプロジェクトの協調（meta/adr/0023）**: 複数プロジェクトが契約で交わる場合（consumer-driven
contract。UIの設計がバックエンド契約の形を駆動してよい）は、フロントが契約に対して作り・バック実装は
独立トラックで進める縦順序を守り、プロジェクトをまたいでPRを交互に出さない。越境（あるプロジェクトの
成果物が別プロジェクトの契約起草を要求する状況）は、人間のauthorizeを経てarchitectが直接行ってよい。
詳細はmeta/adr/0023参照。

## 5. エスカレーション

どのagentも、担当範囲で契約と矛盾を検知したら permissions.md のエスカレーションプロトコルに従う。
agent間で解決しない（例: developerとtesterの解釈が割れる、architectとdesignerのreconciliationで
食い違う）場合も同様に、矛盾分析レポートで人間に判断を仰ぐ。

## 6. orchestratorの制約（meta/adr/0011）

agentを起動し成果物を束ねる役（orchestrator）は、4agentのような役割定義ファイルを持たないが、次の制約に従う。

**ディスパッチ・プロンプトに書いてよいのは routing だけ**:
1. タスクの同定（どのスライス／タスクか）
2. 読むべき成文ソースの指定（既にある文書への参照）
3. 産出物の指定
4. 既存ルールの発動（例: ADR-0009で申し送りを確認せよ）

**書いてはならない**: ドメインルール・設計制約・解釈・答えといった実質的内容。これらをプロンプトに注入すると、(a)非ルーチン・非バージョン管理になり（P-04）、(b)orchestratorが劣化・バイアスの点になり（FR-006と同型）、(c)agentの独立導出を短絡させる（tester/reviewer分離が防ぐ「誤解の自己申告」と同じ失敗）。

注入したくなったら、それは成文ソースの不足のサイン。まずソース（役割定義／ADR／契約／activeContext）に足してagentに読ませる。新規のドメイン判断が要るなら人間に回す。

**実質的成果物を自ら作らない（meta/adr/0014）**: orchestratorは発見・routing・機械検証での確認だけを行う。実装コード・steps/dsl・契約はagentが作る。検証インフラのうち、ロジックを持つもの（build.gradle・govlint等）はdeveloperの領分（テスト付き）、薄い宣言的なCIワークフロー（.github/workflows/）のみorchestratorが直接編集してよい（PRのCIで自己検証されるため。ゲート変更は人間承認）。検証インフラの問題は発見即修正（自己採点）せず、修正をdeveloper/testerに委譲してフローに載せる。

**例外（meta/adr/0021）**: designerの(b)外部AI実行は、orchestratorが依頼を受けて代行する。これは
developerが用意したツール（`meta/tools/commission_design_api.py`）を、designerが指定したパラメータ
（ブリーフのパス・モデル名・出力先）で機械的に実行し、結果を無改変で返すだけの代行であり、
orchestrator自身の判断・解釈が入る余地はない。ドメインルール・設計制約・解釈の注入（本節が禁じる行為）
にも、実質的成果物の自己生成（同じく本節が禁じる行為）にも当たらない。

**agent/orchestratorは外部成果物を手で書き直さない（meta/adr/0020・0021）**: designer以外のagent・orchestratorも、外部AIの成果物を静的HTMLや別形式に手で翻訳してレビューに供してはならない。再実装は成果物の質を変容させる。無改変での受け皿配置のみが正しい経路である。**この無改変原則は人間レビュー前に適用される**。人間レビュー後は、developerが実装統合・構造適合のための改修を行ってよい（作り直しではなく既存TSXの調整として行う。おおまかなコンポーネント構成を保つ限り操作感・細かいUIの洗練は自由、骨格を変える改修は人間承認を要する。meta/adr/0021）。
